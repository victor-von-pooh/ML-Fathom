# 設計

ML-Fathom の今の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) に置く.

## 1. 役割と位置づけ

機械学習に使うデータを, 画面の上で読み込み, 探索的に分析し (EDA), 前処理をして, 学習 (ML-Found) にそのまま渡せる形に書き出すローカルの Web アプリ. 「機械学習を全て GUI 上で行う」アプリ (問題の設定, データの分析, モデルの作成・選定, 学習・評価, 推論の段階に分けて作る) のうち, 「データの分析」の段階の画面.
コードを書かずに, データの形と特徴をつかみ, 学習の前に確かめた方がよいこと (気付き) を見て, 前処理の手順を組み立てる.

- 将来は他の段階の画面と 1 つのアプリ (殻) にまとめる. そのため構成と道具を ML-Dashboard と ML-CreateArchitecture にそろえる

| 部分 | 中身 |
| --- | --- |
| バックエンド | Python, FastAPI. ML-EDA を呼ぶ API, 登録したデータの一覧, データごとのレシピ, 書き出したデータセットの置き場 |
| 画面 | TypeScript, React, Vite, React Router. グラフは ECharts (ML-Dashboard と同じ) |

### 役割

- 前の段階 (問題の設定の ML-Pathfinder) から, 問題 (`problem.yaml`) と, 元のデータの場所と読み方を受け取る. 問題から始めると, データの登録と, 目的の列, 分割, 除く列を決めたレシピの雛形が入った状態になる
- 後ろの段階へ渡すのは, 書き出したデータセット (学習・評価の ML-Dashboard と ML-Found が読む. 問題に学習のプロジェクトの記録があれば `project.dataset` へ直接) と, 問題への書き戻し (ここで変えた列の使い方). モデルの作成・選定の ML-CreateArchitecture は書き出したデータセットのモデルの入力 (ML-EDA の `model_inputs`) を読む
- 読み込み, 分析, 気付き, 前処理, 書き出しは ML-EDA が行い, このアプリは画面と, 登録したデータとレシピの置き場を受け持つ

### 要件

段階として要ることを挙げる (データの種類ごとではない. 種類ごとの分析は下の各章).

| 要件 | 今できていること | 足りないこと |
| --- | --- | --- |
| データを読み込み, 登録できる | 場所を選んで読み込みの候補から登録する. 読み込みの設定を変える. 見本のデータを作る. 表, 時系列, 画像, 文, 点群, 多視点の撮影, 音声, 記録した軌跡 | 偏りのある介入の記録と, 自己教師のコーパス, 多モーダルのデータ (ML-EDA が持つのを待つ. TODO.md の条件待ち) |
| データの形と特徴をつかめる | 概要と気付き, 列, 関係, 見本のタブ. 型ごとの分析 (軌跡, 並べるの反応の表, 群分け, 異常の検知, 介入の記録, 値段を変えた記録, 需要の記録) | 群の安定性を問題の答えで数える (ML-Quest が問うのを待つ. TODO.md の条件待ち) |
| 前処理の手順を組み立てられる | レシピ (手順の並びと分割) を組み, 試し, 保存する. 気付きから手順を選ぶ | 無し |
| 学習に渡せる形に書き出せる | 版 1 (表), 版 2 と版 3 (ファイルの組), 書き出したデータセットの一覧. 問題の学習のプロジェクトの記録があれば `project.dataset` へ書き出す | 無し |
| 問題から始め, 書き戻せる | 問題の一覧 (ML-Pathfinder の置き場から), 始める, 食い違いを見る, 選ぶ問いに答えて書き戻す (中身の印で他での書き換えを確かめる). 殻で選んだ問題から始め, そこから始めたデータに一覧を絞る (「3. 画面」の「殻で選んだ問題」) | 無し |
| 1 つのアプリの中の段階として動ける | 単独で起動でき, 置き場 (`ML_FATHOM_HOME`), トークン, 受け付けるホスト名を `create_app` に渡せる. 確かめを持たない API だけのアプリ (`create_api`) を殻の頭の下に mount できる (「4. API」). 画面の根の部品 (`StageApp`) に経路の頭, API の頭, 殻で選んだ問題を渡して載せられる (「3. 画面」の「根の部品」) | 下の「統合に向けて足りないこと」 |

### 統合に向けて足りないこと

統合先は新しいリポジトリ ML-Studio (殻). 5 つのアプリを submodule で持ち, 1 つのコマンドで 1 つのポートで起動する. 起動ごとのトークンと Origin の確かめは殻が 1 つだけ持つ. 各アプリは今まで通り単独でも動く.

- **言葉**: 段階の名前 (データの分析) と画面の言葉を 5 つのアプリでそろえる. 見出し, 段階の並び, 誤りの出し方は殻の共通の部品にそろえる

## 2. 使うライブラリと約束

ライブラリは ML-EDA (submodule. ML-Dashboard と ML-Found, ML-CreateArchitecture と ML-ModelControl の関係と同じ). 問題を読み書きするために ML-Quest も submodule にする.

- 読み込み, 分析, 気付き, 前処理, 書き出しは全て ML-EDA が行う. このアプリは画面と, 登録したデータとレシピの置き場だけを受け持つ
- 読み書きするファイル:

| ファイル | 読むか書くか | 約束 |
| --- | --- | --- |
| 元のデータ (表, 時系列, 画像, 文, 点群, 多視点の撮影, 音声) | 読むだけ | ML-EDA の読み込み. 書き換えない |
| 記録した軌跡 (`<名前>.csv` か `<名前>.parquet` と, 説明の `<名前>.json`) | 読むだけ | ML-EDA の「記録した軌跡」の約束 (`load_trajectory` で読み, `describe_trajectory` で要約する). 書き換えない (下の「12. 記録した軌跡の分析」) |
| 軌跡の分析 (`<軌跡の名前>.analysis.json`) | 書く (ブラウザで保存) | ML-EDA の `describe_trajectory` の結果のまま (下の「12. 記録した軌跡の分析」) |
| 並べるの反応の表 (問題に入れた, 1 行が 1 つの反応の表のファイル 1 つ) | 読む, 学習のプロジェクトに写す | ML-EDA の「並べるの反応の表」の約束 (`load_reactions` で読み, `describe_reactions` で要約する). 元のファイルは書き換えず, 前処理をかけないファイル 1 つのまま `project.dataset` に写す (下の「13. 並べるの反応の表の分析」) |
| 介入の記録の表 (登録した表と時系列のうち, 処置の列と結果の列を持つ表) | 読む, データセットに書く | ML-EDA の「介入の記録の要約」の約束 (`describe_uplift` で処置の群と対照の群の数, 結果の差, 釣り合いと気付きを求める) と「介入の記録の表」の約束 (版 1 の `task: uplift` で書く). 元のファイルは書き換えない (下の「16. 介入の記録の表の分析」) |
| 値段を変えた記録の表 (登録した表と時系列のうち, 値段の列と売れた数の列を持つ表) | 読む, データセットに書く | ML-EDA の「値段を変えた記録の要約」の約束 (`describe_price` で値段の幅と数, 値段と売れた数の関わり, 商品ごとの試した値段, 値段と他の列の関わりと気付きを求める) と「値段を変えた記録の表」の約束 (版 1 の `task: price` で書く). 元のファイルは書き換えない (下の「17. 値段を変えた記録の表の分析」) |
| 需要の記録の表 (登録した表と時系列のうち, 商品の id の列, 日付の列, 日ごとの売れた数の列を持つ表) | 読む, データセットに書く | ML-EDA の「需要の記録の要約」の約束 (`describe_demand` で日付の範囲, 売れた数, 曜日ごとの売れた数, 商品ごとの記録の日数と抜けの日, 在庫が 0 の日と気付きを求める) と「需要の記録の表」の約束 (版 1 の `task: demand` で書く). 元のファイルは書き換えない (下の「18. 需要の記録の表の分析」) |
| 群分けの表 (登録した表と時系列のうち, 正解の無い 1 行が 1 つの対象の表) | 読む, データセットに書く | ML-EDA の「群の要約」と「群分けの表」の約束 (`describe_groups` で学習に通さず群の要約を求め, `export_group_rows` で分析の保存として版 2 のデータセットに書く. 版 2 は学習には使わない). 学習へは表のファイルを渡す. まとめるの問題から始めた表は, 前処理をかけないファイル 1 つのまま `project.dataset` に写す (ML-Quest のまとめるの骨組みは表のファイルを問題の読み方で読むため). 元のファイルは書き換えない (下の「14. 群分けの表の分析」) |
| `dataset.yaml` と書き出したデータセット | 書く, 一覧で読む | ML-EDA の約束. 版 1 (1 件 = 1 行の表. `load_dataset` で読む) と版 2, 版 3 (入力と正解がファイルの組. 版 3 は項目ごとに書き出しでかけた中身の手順 (`steps`) を持つ. どちらも `load_items` で読む. 読む版の組は ML-EDA の `ITEMS_FORMAT_VERSIONS`). 知らない版は「読めない版」と出す (下の「8. データセットの一覧」). モデルに要るものは版 1 も版 2 と版 3 も ML-EDA の `model_inputs` で読む. 版 1 の異常の検知 (`task: anomaly`) は ML-EDA の「異常の検知の表」の約束 (レシピの `id` と `split.unlabeled: normal`, 説明の `anomaly`) で書き, 一覧で `anomaly` を読む (下の「15. 異常の検知の表の分析」). 版 1 の効果を見積もる (`task: uplift`) は ML-EDA の「介入の記録の表」の約束 (レシピの `treatment`, `outcome`, `id` と `split.method: stratified`, 説明の `uplift`) で書き, 一覧で `uplift` を読む (下の「16. 介入の記録の表の分析」) |
| `problem.yaml` (問題) | 読む, 書き戻す | ML-Quest の形. 版 1 と版 2 を読み, 版 2 で書き戻す. ML-Pathfinder の置き場の `problems/<識別子>/problem.yaml` を一覧にする. ML-Quest が学習のプロジェクトを作ったときの記録 (`project.path`, `project.dataset`, `project.model_spec`. 書いていない問題もある) を読み, `project.dataset` を書き出し先にする (`project.model_spec` は一覧で返すだけ) (下の「11. 問題から始める」) |
| レシピ (`recipes/<ID>.yaml`) | 読み書き | ML-EDA のレシピの形 |

- 目的の列とタスクの種類は画面で選ぶか, 問題から受け取る
- アプリのコードは ML-EDA と ML-Quest の公開の名前 (`__all__`) だけを使う (中の作りが変わっても画面が壊れないように). 公開を待つ名前を使う場合は `tests/test_public_names.py` の表 (`WAITING`) に置き, 待っている理由を TODO.md に書く (今は無し). 組のライブラリに別名を付ける import (`import ml_eda as e`) は, 別名の後の名前を確かめられないので使わない. JSON の応答にする変換 (`to_json`) は画面の受け持ちなので, このアプリが持つ. ML-EDA の分析の結果と NaN の扱いがずれないよう, ML-EDA の `profile.to_json` と同じ決まりにする

## 3. 画面

1. **データ**: 登録したデータの一覧. 「見本のデータを入れる」で, 操作を試すための見本 (顧客の解約の表, 電力の使用量の時系列, 図形の画像, レビューの文, 物体の点群. どれも学習の前に直すことを含む) を置き場の `samples` に作って登録する. 「データを登録」で, ディレクトリをたどってファイルかディレクトリを選び, ML-EDA が判定した読み込みの候補 (確からしさの順) から選んで登録する
2. **データごとの画面**: 上で目的の列を選ぶ (分析に目的の列との関係が加わる). 表の読み込み (csv, json, parquet, excel) は「読み方」で, 自動, 表 (日時の列があっても時系列にしない), 時系列 (時刻の列), 文 (文の列. 語の番号の並びにして学習する) を選べる (ML-EDA の読み込みの kind, time_column, text_column). 「読み込みの設定」で, 読み込みのその他の設定 (Excel のシート, 区切り文字, 文字コード, ヘッダーの行など. ML-EDA の読み込みが持つもの) を変えられる. 空の欄は読み込みが推定する. 真偽の設定 (画像の `digest`, 画像, 点群, 撮影, 音声の `follow_links`) は既定, true, false から選ぶ (取り違えた文字を送らないように). 読めない設定は保存しない. 分析に失敗しても直せるように, 分析の結果が無いときも出す タブで切り替える
    - **概要と気付き**: 種類, 行, 列, 欠損, 重複, メモリと, 気付きの一覧 (列の名前を押すとその列の詳細へ). 前処理のタスクが異常の検知の表と時系列は, 異常の正解の数も出す (下の「15. 異常の検知の表の分析」の「正解の数と異常の割合」)
    - **列**: 列の一覧 (型と気付きの印) と, 選んだ列の統計とグラフ (数値はヒストグラム, カテゴリは頻度, 文は長さと頻出語)
    - **関係**: 目的の列の分布と, 各列との関連の強さ. 数値の列の相関 (Spearman と Pearson) と, カテゴリの列の関連 (Cramér の V) のヒートマップ
    - **時系列** (時系列だけ): 時刻の間隔, 抜け, 期間, 系列のグラフ (範囲を変えられる), 自己相関と周期の候補
    - **中身を見る** (画像, 文, 点群): 件数, 大きさや点の数の分布, 読めないファイルの数と, 1 件ずつの中身 (画像は並べて, 文は一覧, 点群は回せる 3D 表示). ラベルやファイルの名前で絞り込める. 読めない件は, 一覧に表の `error` の理由 (外を指すリンクなど) を出し, 画像はその件の中身を読みに行かない. 点群, 音声, 撮影で選んだ件が読めなければ, 1 件の中身の API の理由を出す
    - **中身を見る** (音声. ML-EDA の `audio`): 件数, 標本化の周波数とチャンネルの数の内訳, 長さ (中央値と範囲), 読めないファイルの数と, 一覧 (ラベル, 周波数, チャンネル, 長さ) から 1 つを選ぶと, その音声の再生 (ブラウザの音の再生の部品) と波形. 再生と波形は先頭の 30 秒だけ (長い録音で大きな音を送らないように. 切った場合はそう添える). 波形はチャンネルを平均した振幅を区間ごとの最小と最大で描く
    - **中身を見る** (多視点の撮影. ML-EDA の `capture`): 撮影の一覧 (枚数, 信頼できる深度の割合, 方位の隙間) から 1 つを選ぶと, 上から見たカメラの配置 (ML-EDA の `capture_layout`. 物の中心と各カメラ, 追跡できなかった枚, 最も大きい隙間の向き), 各枚の画像の小さな一覧 (画像, 深度, 信頼度を切り替える. 深度は欠けを除いた 2 % 点から 98 % 点で明るさにする (遠い数画素で全体が暗くならないように). 信頼度は値のまま), 撮影に点群があれば回せる 3D 表示. 版 1 の前処理と書き出しは ML-EDA が撮影を扱わないので, 前処理のタブはそう知らせ, 撮影と点群の対の書き出し (下の「9. ファイルの組の書き出し」) へ案内する
    - **群分け** (表と時系列だけ): 群を作る列と群の数を選んで, 学習に通さずに作った群の要約を見て, 群分けの表を分析用に書き出す (分析の保存). まとめるの問題から始めた表は, 問題の答えで欄を埋めて開き, 学習のプロジェクトへ表のファイルを書き出せる (下の「14. 群分けの表の分析」)
    - **表の中身**: 並べ替え, 絞り込み, ページ送り. 値は ML-EDA の `frame_view` の形 (前処理の前と後と同じ見え方にするため). 欠損と無限大は「欠損」と出す
    - **前処理と書き出し**: 下
    - 記録した軌跡は, 上のタブの代わりに軌跡の分析のタブを出す (下の「12. 記録した軌跡の分析」)
    - 並べるの問題から始めた反応の表は, 上のタブの代わりに反応の表の分析のタブを出す (下の「13. 並べるの反応の表の分析」)
3. **データセット**: 書き出したデータセットの一覧 (下の「8. データセットの一覧」. 表のデータセットとファイルの組のデータセットはモデルに要るもの (入力の形と型, 文なら語彙の大きさ, 出す値の数) も出し, 異常の検知のデータセットは正解の数と異常の割合と分割ごとの行の数も, 効果を見積もるのデータセットは分割ごとの処置の群と対照の群の行の数と結果の差も, 値段を変える判断のデータセットは分割ごとの値段の範囲と売れた数の平均も, 時間をまたぐ量の判断のデータセットは分割ごとの発注を決める日の範囲と期間の合計の平均も出す). 「ファイルの組を書き出す」で, 入力と正解がファイルの組のデータセット (版 2. 中身の手順をかければ版 3) を書き出す画面に移る (下の「9. ファイルの組の書き出し」)

画面の部品は, 殻の通しの確かめと読み上げで役割と名前で選べるようにする.

- 見出しを持つ欄 (カード) は, 見出しを名前にした区域 (region) として読み上げる. 見出しの無い欄は名前を持たない. 見出しにボタンやリンクを含む欄は, それを除いた名前を区域の名前として渡す (区域の名前にボタンの名前が混ざらないように)
- 数の決まらない, 同じ形を繰り返す欄 (データセットの一覧のデータセットごとの欄) は区域にしない (見出しは h2 のまま). 区域が数十並び, 区域を順に移る読み上げの邪魔になるため. 1 つの画面に決まった数だけ出る欄 (選んだ問題, 学習のプロジェクトへ書き出す, 目的と分割など) は区域にする

### 根の部品

画面のパッケージ (`frontend`) は, 段階の画面の根の部品 `StageApp` (`src/StageApp.tsx`) と, 段階に固有の CSS (`src/stage.css`) を公開する (`package.json` の `exports` の `.` と `./stage.css`). 殻は自分の画面のビルドにこの 2 つを取り込む (ML-Studio の設計の「画面: 根の部品」). 単独の起動では `main.tsx` が既定の値で `StageApp` を描く.

| props | 型 | 意味 | 単独の値 |
| --- | --- | --- | --- |
| `basename` | `string` | 画面の経路の頭 (例 `/data`). 経路 (`/`, `/sources/:id`, `/datasets`, `/datasets/export`) と移動先はこの下 | `""` |
| `apiBase` | `string` | API の頭 (例 `/api/data`). API の呼び出しと, 画像, 音声, 撮影の枚の URL は全てこの下 | `"/api"` |
| `project` | `string \| null` | 殻で選んだ問題の識別子 (ML-Pathfinder の問題の置き場の `<識別子>` ディレクトリの名前). null なら選んでいない | `null` |
| `onProjectChange` | `(project: string \| null) => void` | 部品の中で置き場の問題から始めたときに, その識別子で呼ぶ | 何もしない |
| `onProjectsChange` | `() => void` | 呼ばない (このアプリは問題を作らず, 消さず, 名前を変えないので, 一覧は変わらない) | 何もしない |
| `embedded` | `boolean` | 殻の下か. true なら左の欄のアプリの名前と明暗の切り替えを出さない (左の欄の「データ」と「データセット」は出す) | `false` |

- 部品は自分のルーター (`BrowserRouter` に `basename`) と TanStack Query の client を持つ (殻に中の作りを出さないため). API の頭は部品の中で 1 度決めて context で渡し, 画面の部品は `useApi()` で呼び出しの一式を取る (呼び出しごとに頭を渡し忘れないため)
- 画面のソースでは根から始まる絶対パスを使わない. 移動は `Link` と `navigate` で `basename` の下にし, `window.location` を書き換えない (殻の下では根が殻の画面を指すため). `index.html` の `/favicon.svg` は単独の起動のためのもの
- 明暗は `html` 要素のクラス `dark` と `localStorage` の `theme` で持つ. 単独では切り替えで両方を書き, `index.html` が描画の前に読む. `embedded` では書かずに読むだけにし, `html` のクラスの変化を見て読み直す (殻の切り替えで, CSS の変数から色を読むグラフと点群も描き直すため)
- CSS の変数 (`cssVar`) から読む色は描画の中で読まず, 描く時 (effect) に読む. グラフの設定で色を読む場合は `Chart` の `option` を設定を返す関数で渡す (単独では描画の後に `html` のクラスを替えるので, 描画の中で読むと切り替えの前の色が残るため)
- `stage.css` は段階に固有の CSS (Tailwind の読み込みと色のトークン以外. 数の桁をそろえる `.tabular`). 単独では `index.css` が Tailwind と色のトークンと一緒に読む

### 書きかけの下書き

殻の要求 R10 (離れるときに書きかけを捨てない) に合わせ, 打ち直すのに手間のかかる欄は書きかけを変えるたびにブラウザ (`localStorage`) に残し, 部品が次に開いたときに戻す (殻の中の移動はページを閉じず, 部品は移動を止められないため).

| 欄 | 下書き |
| --- | --- |
| 前処理と書き出しのタブの編集中のレシピ (手順の並びと分割) | 残す. データごとに `ml-fathom:draft:<データの ID>`. 変えるたびに書き, 保存するか, 読み方を変えるかデータを消すと消す |
| 気付きのカードの「決めた」の印 | 残す. データごとに `ml-fathom:decided:<データの ID>` |
| ファイルの組の書き出しの欄 (ディレクトリ, 分割, 正解の出どころ, 中身の手順) | 残さない. 問題から始めた場合は開くたびに問題の値で埋め直す. 手で始めた場合は TODO.md |
| 選ぶだけか数 1 つの欄 (目的の列, 読み方, 読み込みの設定, 群分けの列と群の数, 書き出しの名前と上書きの印) | 残さない (前の値のまま書き出す誤りを避けるため) |

### 殻で選んだ問題

殻で選んだ問題 (`project`) は問題の識別子で, このアプリではデータの記録の `problem` (始めた `problem.yaml` の場所) の親のディレクトリの名前に対応させる (識別子は置き場の `<識別子>/problem.yaml` のディレクトリの名前のため).

- `project` があれば, データの一覧の上に, 置き場の一覧 (`GET /problems`) のうち場所の親のディレクトリの名前が `project` の問題の名前と「この問題から始める」を出す. 始める流れと始めた後の移動先は「問題から始める」の対話と同じ (下の「11. 問題から始める」). 始められない問題は理由を出してボタンを出さず, 置き場に無い識別子は無いと出す
- `project` があれば, データの一覧はその問題から始めたデータ (`problem` の親のディレクトリの名前が `project`) に絞る. 「全てのデータを出す」で絞りを外せる (他の問題のデータや, 問題から始めていないデータも開けるようにするため). 外したのはそのときの問題だけで, 殻で選び直すとまた絞る
- 部品の中 (「問題から始める」の対話か一覧の上の欄) で置き場の問題から始めたら, その識別子で `onProjectChange` を呼ぶ. 識別子が `project` と同じなら呼ばない (殻と部品の間で知らせが行き来し続けないため). 置き場の外の `problem.yaml` から始めたときは, 同じ名前のディレクトリでも呼ばない (殻の問題の一覧に無い識別子を渡さないため). 置き場にあるかは, 始めた場所と一覧の場所 (どちらも実際のパス) を比べて決める
- 殻が `project` を替えたら, データの一覧に移す (選んだ問題の欄と絞った一覧を見せるため). 部品が `onProjectChange` で知らせた値が返ってきたときは移さない (始めた後のデータの画面に留まるため). 最初に受け取った値では移さない (開いた URL のまま描くため)
- `project` が null なら, 一覧の上の欄を出さず, 絞らない

## 4. API

単独の起動では全て `/api` の下. 起動ごとのトークン (Cookie か `x-fathom-token` ヘッダー) が要る. 殻の下では下の表の `/api` が殻の頭 (`/api/data` など) に替わる.

### アプリの組み立て

API と, 確かめと画面の配信を, 2 つの FastAPI のアプリに分ける (殻の下では確かめを殻の 1 つだけにするため).

- `create_api(data_dir=None, *, problems_dir=None)`: API だけのアプリ. 殻はこれを `/api/data` のような頭の下に mount する
    - 6 つの router (`api`, `problems`, `groups`, `uplift`, `price`, `demand`) は全て頭なし (`APIRouter()`) で, このアプリに加える. mount の下の経路の照合は mount の頭を除いた経路で行われるため
    - トークン, Origin, ホスト名の確かめ, `/api/auth`, 画面の配信を持たない (載せる側が持つ). 仕様の画面 (`/docs`, `/redoc`, `/openapi.json`) も閉じる
    - 置き場は `app.state.store` (登録したデータ, レシピ, データセット) と `app.state.problems_dir` (ML-Pathfinder の問題の置き場) に持ち, ルートは `request.app.state` から取る. Starlette では mount した sub-app の中の `request.app` は sub-app を指すので, 殻の下でもルートはそのまま動く
    - `data_dir` はこのアプリのデータの置き場 (無ければ既定の置き場. 下の「6. 置き場」). `problems_dir` は問題の置き場. 渡さなければ作ったときの `ML_PATHFINDER_HOME` (無ければ既定) の下の `problems`. 殻は ML-Pathfinder と同じ置き場を渡す
    - 例外ハンドラ, 子プロセス, プロセス全体の登録簿は持たない
- `create_app(data_dir=None, token=None, allowed_hosts=None)`: 単独で起動するアプリ. 確かめ (トークン, Origin, ホスト名), `/api/auth`, 画面の配信を持つ外側のアプリに, `create_api(data_dir)` を `/api` で mount する. 確かめは外側の middleware なので, mount した API にも効く. `/api/auth` は mount より先に登録し, 画面の配信 (他のパスは index.html) は最後に置く. `/api` ちょうどと `/api/` の下の無いパスは画面でなく 404 を返す. 仕様の画面 (`/docs`, `/redoc`, `/openapi.json`) は外側のアプリでも閉じる (トークン無しで API の形を見せないため)
    - `token` が `None` か空の場合は, 環境変数 `ML_FATHOM_TOKEN` (無いか空ならランダム) を使う. 環境変数も無いか空の場合は開き方の URL (`/api/auth?token=...`) を表示する (空のトークンでは誰でも API を呼べるため)
    - 画面の配信は GET と HEAD を受け付ける. 画面の置き場にあるファイルはそのまま返し, それ以外の経路は `index.html` を返す (画面の中の移動先のため). NUL の字を含む経路や長すぎる名前のように, ファイルとして調べられない経路も `index.html` にする
- 仕様の書き出し (`ml-fathom --openapi`) は `create_api` の仕様のパスに `/api` を付けて書き出す (外側のアプリの仕様には mount した API が入らないため)
- ポートはアプリが持たず, 起動の `ml-fathom --port` (か殻) が決める

| `POST /api/sources/{id}/problem/write` | 選んだ答えとともに問題に書き戻す |

## 5. 用語

段階をまたいで出る物と操作の語 (問題, 学習のプロジェクト, 段階の名前, 書き出す, 書き戻す, 上書き, 登録する, 誤り, 失敗など) は, 殻 ML-Studio の設計の「5. 用語」の「段階をまたぐ言葉」の表に従い, ここには表を置かない (2 か所に表を置くと食い違うため). 画面では 1 つの問題を「問題」と呼び, 「問題の設定」は段階の名前だけに使う. 学習のプロジェクトは縮めずに「学習のプロジェクト」と書く (この段階は学習・評価の段階でないため). 他の段階は段階の名前で呼ぶ (単独の起動の左の欄の「ML-Fathom」は除く). 次の表はこのアプリに固有の語.

| 用語 | 意味 |
| --- | --- |
| データ | 登録した分析するファイルかディレクトリ. 登録しても元のファイルは変えない |
| 種類 | ML-EDA が判定したデータの形. 表, 時系列, 画像, 文, 点群, 多視点の撮影, 音声. 記録した軌跡 (`trajectory`) は, このアプリが ML-EDA の `load_trajectory` で読めるかで決める. 並べるの反応の表 (`reactions`) は, 並べるの問題から始めたかで決める |
| 反応の表 | 並べる (推薦) の学習に使う, 1 行が 1 つの反応 (利用者が品物を買った, 見たなど) の表. 利用者, 品物, 時刻の列と, 任意の反応の強さの列 (ML-EDA の「並べるの反応の表」) |
| 群の要約 | 群分け (まとめる) で, 群ごとの行の数, 割合, 安定性と, 群を作った列の要約 (数の列は平均, 他の列は最も多い値と割合) を並べた表と, 群全体の安定性 (調整ランド指数) とまとまり (シルエット係数) (ML-EDA の「群の要約」) |
| 群分けの表 | 群分け (まとめる) の, 正解の無い 1 行が 1 つの対象の表. 学習へは表のファイルのまま渡す. 分析の保存として版 2 の受け持ち `group` のデータセットにも書ける (ML-EDA の「群分けの表」) |
| 異常の検知の表 | 正常の行が多く, 異常の正解が無いか少しだけある表 (機械のセンサの値や取引の記録など). 正常の行だけで学ぶために版 1 の `task: anomaly` で書き出す. 目的の列は異常の正解の列 (異常は 1 か真, 正常は 0 か偽. 無くてもよい) (ML-EDA の「異常の検知の表」) |
| 介入の記録の表 | 過去に行動した記録の表 (クーポンを配った記録など). 顧客の特徴の列, 処置の列 (配ったか. 1 か真, 0 か偽), 結果の列 (買ったか, または買った額). 顧客ごとの効果 (uplift. 処置したときの結果 − しないときの結果) を見積もるために版 1 の `task: uplift` で書き出す. 処置は無作為に配った記録を前提にする (ML-EDA の「介入の記録の表」) |
| 処置の群, 対照の群 | 介入の記録の表で, 行動した (処置の列が 1 の) 行と, しなかった (0 の) 行 |
| 釣り合い | 処置の群と対照の群で, 特徴の列の分布がそろっているか. 標準化した平均の差 (SMD) で測る (ML-EDA の「介入の記録の要約」) |
| 値段を変えた記録の表 | 過去の売れ行きの記録の表. 商品の特徴の列, 値段の列, 売れた数の列, 原価の列 (任意), 商品の id の列 (任意). 値段を入力に入れて売れた数を予測し, 商品ごとに利益が最も大きい値段を選ぶために版 1 の `task: price` で書き出す. 値段は試しに変えた記録 (無作為に近い) を前提にする (ML-EDA の「値段を変えた記録の表」) |
| 値段, 売れた数, 原価 | 値段を変えた記録の表の, 売ったときの値段 (0 より大きい数), その値段で売れた数 (0 以上の数), 商品 1 つを仕入れるか作るのにかかる値段 (0 以上の数). 利益は (値段 − 原価) × 売れた数 |
| 弾力性 | 値段を 1 % 上げたときに売れた数が何 % 変わるかの目安 (ML-EDA の `describe_price` の `elasticity`). 負なら値段を上げると売れた数が減る |
| 値段の段 | 値段を変えた記録の表で, 行を値段の順位で 5 つに等しく分けたもの. 書き出しの分割の層と, 要約の値段と売れた数の関わりに使う (ML-EDA の「値段を変えた記録の表」) |
| 値段の手順 | 値段の列にかけられる手順 (`clip`, `log`, `standardize`, `minmax`). 候補の値段にも同じ当てはめた値でかけ直すため, 他の手順は値段の列を変えられない (ML-EDA の「値段を変えた記録の表」) |
| 需要の記録の表 | 商品ごとの日ごとの売れた数の記録の表 (時系列). 商品の id の列, 日付の列, 日ごとの売れた数の列, 商品の特徴の列, 在庫の数の列 (任意). 先の決めた期間の需要 (売れる数の合計) を分位点で予測し, 品切れの損と売れ残りの損の比から決まる分位点で発注の数を決める (時間をまたぐ量の判断) ために, 版 1 の `task: demand` で書き出す (ML-EDA の「需要の記録の表」) |
| 先の期間, 前の期間 | 需要の記録の表で, 発注を決める日から先の期間の日数 (`horizon`) の日 (その日を含む) と, その日の前の同じ日数. 先の期間の売れた数の合計が書き出しの正解 (`demand`), 前の期間の合計が比べる相手 (`demand_previous`) |
| 発注を決める日 | 需要の記録の表で, 書き出しの 1 行になる (商品, 日) の日. 記録の最初の日から発注を決める日の間隔 (`interval`. 既定は先の期間の日数) ごと |
| 抜けの日, 在庫が 0 の日 | 需要の記録の表で, 商品の最初の日から最後の日の間の, 行の無い日 (と売れた数の欠けた日) と, 在庫の数が 0 の日 (売れた数が品切れで抑えられ, 需要より少なく記録された日) |
| 度合い | 異常の検知で, 学習したモデルが行ごとに出す異常らしさの数 (大きいほど異常らしい). 自己符号化器の作り直しの誤差か, 正常の行からの距離 |
| 軌跡 | 強化学習の方策を環境で走らせた記録. 1 歩が 1 行の表と説明 (ML-EDA の「記録した軌跡」) |
| 目的の列 | 予測したい列. 画像などはクラスのフォルダの名前 (`label`) |
| 気付き | 学習の前に確かめた方がよいこと (ML-EDA の `findings`). 注意と参考の 2 段階 |
| レシピ | 前処理の手順の並びと分割 (ML-EDA のレシピの形). データごとに 1 つ |
| 中身の手順 | 画像, 文, 点群, 音声の 1 件ずつを同じ形の配列にする手順 (`item_steps`) |
| データセット | 書き出した学習用のデータ (`dataset.yaml` を持つディレクトリ). 版 1 は 1 件 = 1 行の表, 版 2 と版 3 は入力と正解がファイルの組 (版 3 は中身の手順をかけたもの) |

## 6. 置き場

`~/.ml-fathom/` (環境変数 `ML_FATHOM_HOME` で変えられる) に置く. 元のデータのファイルは読むだけで, 書き換えない.

| 場所 | 中身 |
| --- | --- |
| `sources.json` | 登録したデータ (ID, 名前, 場所, 読み込み, 読み込みの設定, 種類, 目的の列, 始めた問題の場所と始めたときの知らせ, 学習のプロジェクトへ書き出した場所) |
| `recipes/<ID>.yaml` | データごとの前処理のレシピ |
| `datasets/<名前>/` | 書き出した学習用のデータセット (ML-EDA の `export_dataset` (版 1) と, `export_image_masks`, `export_capture_clouds` (版 2, 版 3), `export_group_rows` (版 2)) |

読み込んだデータと分析の結果は, ファイルの更新時刻と設定ごとにメモリに覚える (ファイルが変われば読み直す).

問題の一覧は ML-Pathfinder の置き場 (`~/.ml-pathfinder/`. ML-Pathfinder と同じ環境変数 `ML_PATHFINDER_HOME` で変えられる) の `problems/*/problem.yaml` を読む. 2 つのアプリを同じ置き場で使うため, 環境変数も同じものにする. 殻の下では `create_api` の `problems_dir` で問題の置き場を渡す (上の「4. API」).

## 7. 安全

確かめ (トークン, Origin, ホスト名) と `/api/auth` は `create_app` の外側のアプリだけが持ち, `create_api` は持たない. 殻の下では殻が 1 つだけ持つ (段階ごとに確かめが重ならないように). `create_api` を確かめの無いアプリに載せて待ち受けない.

既定では `127.0.0.1` だけで待ち受ける (他のホストを指定すると警告を出す). 起動ごとのトークン (Cookie かヘッダー) を持つ要求だけを API で受け付け, 他のサイトからの書き込み (Origin が接続先と違うもの) と別のホスト名での接続を断る. 手元のファイルを読めるので, トークンは他の人に渡さない. 画像, 点群, 撮影, 音声のディレクトリの中の, 読み込んだディレクトリの外を指すシンボリックリンクは, 既定では一覧, 分析, 1 件の中身, 中身の手順, 版 1 の書き出しのどれでも読まない (ML-EDA の読み込みの決まり. 画面から渡した場所の中のリンクで, 手元の思わぬファイルを見せないため). ファイルの組の書き出し (下の「9. ファイルの組の書き出し」. ML-EDA の `export_image_masks`, `export_capture_clouds`) も, 既定では入力と正解のディレクトリの外を指すリンクの先を写さず, 除いた数と例を書き出しの注意 (`notes`) に出す (ML-EDA の既定 `follow_links=False` のまま). 写すのは, 利用者が書き出しの画面で「外を指すリンクの先も写す」に印を付けた (API の `follow_links` を true にした) 場合だけ (共有の保存先へのリンクで置いたデータを写すため). 印は書き出しのたびに選び, 問題にも残さない (書き換えた問題で, 黙って外のファイルを写させないため). 写すと選んでも, 書き出し先の決まり (学習のプロジェクトの中に限り, 開いた親に対して書く) は変わらない (たどるのは読む側のリンクだけ). 共有の保存先へのリンクで置いたデータは, 読み込みの設定 `follow_links` を true にして読む. データセットの一覧も, 外を指すリンクの `dataset.yaml` は読まない (下の「8. データセットの一覧」). 「学習のプロジェクトへ書き出す」の書き出し先 (`project.dataset`) は, リンクをたどった後も学習のプロジェクトの中のものだけにする (問題のファイルを書き換えて, 外のファイルを上書きさせないため. 下の「11. 問題から始める」). 書き込みの直前には, 親の実体を学習のプロジェクトと比べ直し, 学習のプロジェクトから途中のディレクトリを一段ずつリンクをたどらずに開く (無ければ作る). 確かめの後に別のプロセスが途中の場所をシンボリックリンクかファイルに替えていれば, 理由付きの 422 で断る. 断るか書き出しに失敗すれば, ここで作った途中のディレクトリ (空のもの) を消す (確かめと書き込みの間の差し替えで外に書かせないため). 書き出し先の様子 (無い, データセットか普通のファイル, 他のもの) も, 開いた親に対してリンクをたどらずに確かめる. 反応の表と群分けの表の写しと, 版 1 とファイルの組の書き出し (ML-EDA の引数 `parent` に開いた親の記述子を渡す) は, 開いた親のディレクトリに対して書く (書いている最中に途中の場所が替わっても外に書かないため). 版 1 の書き出しの後のモデルの入力の数も, 開いた親を通して読む (ML-EDA の `model_inputs` の引数 `parent`. パスで読むと替わった先を読むため). 版 1 の書き出しの後に, 書き出し先の親のパスが今も開いた親を通るか (装置と i-node の番号) を比べ, 替わっていれば, データセットを書けた場所 (開いた親の今の場所) を添えて 422 で断る (記録のパスの先には書いていないので). 写しは書き出し先の名前のリンクをたどらずに比べて置き換え, 書き出し先がリンクなら, リンクの先を書き換えず, リンクの項目を写したファイルで置き換える (様子の確かめで断った後にリンクに替わっても外に書かないため. リンクが登録した表そのものを指していても写す).

## 8. データセットの一覧

置き場の `datasets` の下と, 学習のプロジェクトへ書き出した場所 (下の「並べる場所」) の `dataset.yaml` を持つディレクトリを, `format_version` で分けて読む (ML-EDA の `load_dataset` はファイルの組の版で, `load_items` は版 1 で止まるので, 版を見てから読む方を選ぶ). 一覧の 1 件は `form` で形を表す.

- **版 1** (`form: table`): 種類とタスク, 目的の列, 学習に使う列の数, 分割ごとの行数 (`load_dataset`) と, モデルに要るもの (`model`. ML-EDA の `model_inputs` の結果: 入力の名前と形と型, タスク, クラス, 出す値の数). モデルの定義 (ML-ModelControl の `inputs` と最後の層の出す数) をデータに合わせるため. 異常の検知 (`task: anomaly`) は説明の `anomaly` も持ち, 画面は正解の数と異常の割合と分割ごとの行の数を出す (下の「15. 異常の検知の表の分析」). 効果を見積もる (`task: uplift`) は説明の `uplift` も持ち, 画面は分割ごとの処置の群と対照の群の行の数, 結果の平均と差を出す (下の「16. 介入の記録の表の分析」). 値段を変える判断 (`task: price`) は説明の `price` も持ち, 画面は分割ごとの行と商品の数, 元の値段の範囲と種類の数, 売れた数と原価の平均を出す (下の「17. 値段を変えた記録の表の分析」). 時間をまたぐ量の判断 (`task: demand`) は説明の `demand` も持ち, 画面は列と期間, 落とした行の数と, 分割ごとの行と商品の数, 発注を決める日の範囲, 先の期間と前の期間の合計の平均, 先の期間に在庫が 0 の日を含む行の数を出す (下の「18. 需要の記録の表の分析」)
- **版 2 と版 3** (`form: items`. ML-EDA の `ITEMS_FORMAT_VERSIONS` の版): 受け持ち (`role`), 正解の種類 (`target.kind`), 項目ごとの種類, 入力か正解か, 単位, 書き出しでかけた中身の手順 (版 3 の `steps`. 手順と引数を `resize (width 64, height 64)` のように並べる. 推論で新しい 1 件に同じ手順をかけるため), 座標の決まり (撮影は深度の測り方 (`depth`. `z` はカメラの前の軸に沿った距離, `ray` は光線に沿った距離) と画素の中心 (`pixel_center`) を別の行に. 欄の無い撮影には, 書き出し直すと入ると出す), 分割ごとの件数と全ての件数, 正解の出どころ (`target.origin` の種類, 名前, 設定), 正規化をかけたか, 書き出しの注意 (`load_items`) と, モデルに要るもの (`model`. 版 1 と同じく ML-EDA の `model_inputs` の結果: 入力の項目の名前と形と型, 正解の種類 (`target_kind`), 領域のクラスの名前, 出す値の数). 画像と領域は出す値の数を背景を含む領域のクラスの数, 撮影と点群は出す点の数と出す (モデルの定義の入力と最後の層の出す数を, ML-Quest の骨組みが学ぶ形に合わせるため). 形の次元のうち, 決まらないもの (大きさの混ざる画像を手順なしで書き出したものなど) は「不定」と出す. 群分けの表は学習に使わず ML-EDA が受け付けないので, 呼ばずに「群分けの表は学習に使わないので, モデルの入力はありません」と理由を出す. ML-EDA が求められない組 (知らない入力と正解の種類の組) も, 一覧から消さずに理由を出す. 元の場所 (`source`. ML-EDA はディレクトリの名前だけを書く) は出さない. 出どころが `process` (今ある処理の出力) なら, 「測れるのはその処理との一致で, モデルはその処理を超えられない」と短く添える. 項目の種類は日本語の名前で出す (数の値, 種類の値, 画像, 領域など. 知らない種類は「その他の値」). 受け持ちが群分けの表 (`group`) のものは, ファイルの組でなく「群分けの表」と添え, 正解を「正解なし」と出し, 正解の出どころを出さない (正解を持たないため)
- **読めないもの** (`form: unreadable`): 知らない版 (版 1, 2, 3 の他) は「読めない版」として版の番号と理由を出す. 知っている版でも読めなければ, 理由を出す. `dataset.yaml` がデータセットのディレクトリの外を指すリンクなら, 版を読まずに理由を出す (ML-EDA の `load_items` と同じ決まり. ディレクトリ自体のリンクは信頼し, それもたどった後の場所と比べる). 一覧から黙って消さない. `dataset.yaml` の無いディレクトリ (書き出し途中の一時ディレクトリなど) はデータセットではないので並べない
- **並べる場所**: 置き場の `datasets` の下と, 「学習のプロジェクトへ書き出す」で書き出した場所 (登録したデータに持つ `project_dataset`) と, ML-Pathfinder の置き場の問題の学習のプロジェクトの記録の場所 (`project.dataset`. ファイルの組の受け持ちは登録したデータを持たないため). どれも今もデータセットがあるものだけ. 同じ場所は 1 つにする. 学習のプロジェクトのものは `project` にデータか問題の名前を, `project_from` にどちらか (`source` か `problem`) を持ち, 画面は「学習のプロジェクト」と元の名前を添える (版 1 も版 2 も)

## 9. ファイルの組の書き出し

画像と領域の対, 多視点の撮影と正解の点群の対を, ML-EDA の版 2 の約束で書き出す (`export_image_masks`, `export_capture_clouds`). 表の手順をかけず, 1 件ずつのファイルに項目ごとの中身の手順だけをかける (手順が無ければファイルを写す. 撮影と点群は座標の正規化もかける) ので, 登録したデータとレシピを通さず, 2 つのディレクトリを選んで書き出す. 中身の手順をかけたデータセットは版 3 になる (ML-EDA が決める).

- 画面: データセットの一覧の「ファイルの組を書き出す」から移る. 「画像と領域」と「撮影と点群」をタブで切り替える. 版 1 の書き出し (前処理のタブの「保存と書き出し」) と同じく, データセットの名前と「同じ名前があれば上書きする」, 書き出す押しボタン, 書き出した場所と注意と使い方の例を出す
- ディレクトリ: 画像と領域 (それぞれ 2 階層まで. 名前の stem で組にする), 撮影 (撮影のディレクトリか, それを並べたディレクトリ) と点群 (直下の `<撮影の名前>.<拡張子>`). パスを書くか, 「選ぶ」でディレクトリをたどって選ぶ
- 設定: 分割 (自動 (グループがあればグループごと, 無ければ無作為), 無作為, グループごと, 分けない), 正解の無い件 (領域の無い画像, 点群の無い撮影) を除く (既定. 数と例を書き出しの注意に) か `unlabeled` の分割に書くか (ML-EDA の `split.unlabeled`. 除くは既定と同じなので渡さない. 選んだ方の扱いを欄の下に出す. 結果の分割では「unlabeled (正解なし)」と添え, 学習のスクリプトでの使い方に `dataset.split("unlabeled")` の読み方 (正解の項目は None) を足す), 検証用とテスト用の割合, 乱数の種. グループ (任意. 1 行に `件の id,グループ`. 撮影は現場や物で分ける), 正解の出どころ (種類, 名前, 設定 (YAML の辞書)). 画像と領域は値の名前 (1 行に `値: 名前`) と領域のファイルの名前の終わり (`mask_suffix`), 撮影と点群は点群の単位 (`cloud_units`)
- **中身の手順**: 入力と正解の項目ごとに, 1 件ずつのファイルにかける手順を並べる (`item_steps`. 大きさのそろわない画像を学習のコードで毎回そろえず, 推論でも同じ手順をかけられるように). 選べる手順は ML-EDA の手順の登録簿 (`ITEM_STEPS`) から項目の種類で絞ったもの (`GET /api/info` の `pair_steps`): 画像と撮影は `resize`, `grayscale`, `rgb`, 正解の点群は `sample_points`. 他の手順 (`normalize` など) はファイルの形に収まらず ML-EDA が受け付けないので出さない. 領域には ML-EDA が画像の `resize` と同じ大きさの `resize_mask` を自動でかけるので, 領域の欄は出さない. 手順は足した順にかける. 引数 (`width`, `height`, `points`, `seed`) は整数にし, 省けない引数 (登録簿の `required`) が無いか 1 未満 (`seed` は 0 未満) か上限を超えれば書き出す前に止める. 上限は画像の辺 (`width`, `height`) が 4096 画素, 点の数 (`points`) が 100 万点 (大きすぎる値で手元の計算機の記憶を使い切らないため. 版 1 の中身の手順と同じ `STEP_LIMITS`). 上限はバックエンドが持ち (`pair_steps` の `limits`), 画面と API の両方で確かめる. 手順を足さなければ版 2 で書き出す
- **外を指すリンク**: 「外を指すリンクの先も写す」(既定は印なし) に印を付けると, ML-EDA の書き出しに `follow_links=True` を渡し, 入力と正解のディレクトリの外を指すリンクの先も写す. 印が無ければ写さず, 除いた数と例が書き出しの注意に出るので, 結果にこの印で写せることを添える (ML-EDA が返す注意の印の種類 `outside_links` で見分け, 文の言い回しでは見分けない. ML-EDA が文を直しても案内が消えないように. 上の「7. 安全」). 写したものはデータセットの中のファイルになるので, 読む側はリンクをたどらない
- 結果: 書き出した場所, 件数, 書き出しの注意 (組にならなかったファイル, 分割をまたぐグループ, 0 件になった分割など. ML-EDA の `notes`), `load_items` で読む例, モデルに要るもの (一覧と同じ. 書き出した直後にモデルの定義を合わせられるように. 学習のプロジェクトへの書き出しは, 開いた書き出し先の親を通して読む). 書き出せない誤り (EXIF の向きの付いた画像, カラーの領域, 姿勢の無い撮影など) は理由を出して書き出さない
- グループと値の名前と設定の文は画面で辞書にし, 形が誤っていれば書き出す前に止める (書き出しの押しボタンを押せず, 理由を並べる). 欄を変えると前の結果と誤りを消す. タブを切り替えても入れた値は残す
- 書き出し (版 1 も) はアプリの中で 1 つずつ行う (同じ名前の一時ディレクトリを 2 つの書き出しが同時に使わないように). 壊れたファイル (読めない点群など) の誤りも理由を付けて 422 で返す
- **問題から始めた場合**: 「問題から始める」でファイルの組の受け持ちの問題を選ぶと, この画面に問題の場所を付けて移る (下の「11. 問題から始める」). 正解の種類のタブだけを出し (もう一方は問題に合わないため), 欄を ML-Quest の `recipe_from` の書き出しの設定の下書き (ディレクトリ, 分割, グループ, 正解の出どころ, 他の引数) で埋める. 名前の欄の代わりに書き出し先 (学習のプロジェクトの記録の `project.dataset`) とその様子を出し, 「学習のプロジェクトへ書き出す」で書き出す. 書き出し先の決まり (記録が要る, データセットでないものは上書きしない, 前のデータセットは上書きの印を付けた場合だけ上書きする) は版 1 の「学習のプロジェクトへ書き出す」と同じ. 書き出すと, 欄の値を ML-Quest の `apply_recipe` で問題に書き戻す (`data.export`). 書き戻した点と注意の食い違いを結果に出す. 中身の手順も同じ欄で選び, 他の引数と一緒に書き出しの設定の `options.item_steps` に入れる (手順が無ければ入れない). 書き出しにかけ, 問題にも書き戻すので, 開き直すと中身の手順の欄を `recipe_from` の `export.options.item_steps` で埋める (問題から同じデータセットを作り直せるように). 「外を指すリンクの先も写す」は書き出しの設定 (ML-Quest の `data.export`) に持たせず, 書き出しの要求の `follow_links` で送る. 問題には書き戻さず, 開くたびに印なしで始める (外のファイルを写すかは, その場で利用者が決めるため)

## 10. 前処理の組み立て

- 左に目的とタスクと分割, 手順の並び (足す, 消す, 並べ替え, 引数を変える), 保存と書き出し. 右に手順をかけた前と後の表
- 保存していない手順 (編集中のレシピ) はデータごとにブラウザに覚え, タブを移っても, ページを読み込み直しても残す. 保存か書き出しをするか, 読み方を変える (手順が合わなくなる) と消す
- **分割**: 無作為, 層化, 時刻の順, グループごと, グループと時刻の組 (`group_time`. 同じ相手を 1 つの分割にまとめつつ, 後から現れた相手を検証用とテスト用に. 日時の列が要る), グループの層化 (`stratified_group`. 同じ相手をまとめつつ, 目的の値の割合をそろえる. 目的の列が要る), 分けないから選ぶ. グループの層化は, タスクが回帰か時系列の予測なら選べない (目的の値で層を作れないため. ML-EDA の `load_recipe` が止める). タスクを変えて残った場合は, 欄の下に誤りを出す (試した結果も ML-EDA の誤りになる). タスクを決めない場合に目的の値がほぼ全て違うときと, 日時の列や目的の列が無いときは, ML-EDA の誤りを試した結果の所に出す. 時系列で時刻の順を勧める「決めてほしいこと」は, グループと時刻の組を選んでいれば出さない (時刻の順に分けるため). グループの列 (会員の ID のように, 同じ人や物を表す列. ML-EDA のレシピの `split.column`) は, グループごと, グループと時刻の組, グループの層化では分ける単位になり (要る. 欄の空の値は「選ぶ…」), それ以外 (分けないを除く) では任意で選び, 同じ値が複数の分割にまたがるかを確かめる (ML-EDA の `group_overlap`. 時刻の順では参考, 他は注意). 欄を空にするか, 分けないにすると列の指定を消す. 画像は中身の同じファイルが分割をまたぐかを ML-EDA が確かめる (`item_overlap`. `digest` の列). これらの分割の後の気付きは, 学習用のデータの欄に重要度つきで出す (前処理の様子の API の `findings`). 時刻で分ける分割 (時刻の順, グループと時刻の組) を, 時刻の列の無い読み方 (表) で選んだ場合は, 日時に見える列 (日時の型か, よく出る値が全て日付か日時の文字の形の列) があれば, 欄の下に「読み方」を「時系列 (時刻: その列)」にする案内を出す (表として読むと日時の列を時刻に使わず, ML-EDA は「日時の列が要ります」とだけ止めるため)
- **正解の欠けた行**: 目的の列の欠けた行を, 落とす (既定) か `unlabeled` の分割に残すか (ML-EDA のレシピの `split.unlabeled: keep`) を選ぶ. 半教師あり学習や異常の検知のように, 正解の付いた行が少なく, 正解の無い行も学習に使いたい場合のため. 正解の付いた train, valid, test の中身は落とす場合と変わらない. 目的の列が無ければ欄を出さず (ML-EDA では誤りになるので, 目的の列を外したら, 前処理のタブを開いていなくても編集中のレシピ (無ければ保存したもの) から指定を消す. 目的の列を戻しても残すには戻らず, 保存するまで編集中の印が出る), 分析した全ての行で目的の列が欠けていなければ選べない (残すを選んでいる場合は戻せるように選べる). 落とすを選ぶと項目を消す (既定と同じで, 項目の無いレシピと見分けない). 分割の件数とデータセットの一覧では, `unlabeled` を「正解なし」と添えて並べる. 書き出した後の使い方の例は, ある分割 (valid, unlabeled) だけを読む
- 手順の番号を押すと, その手順の前と後を並べる (足した列と消えた列に色). 押していないときは全ての手順の後と, 学習用のデータ (分割ごとの行数, 学習に使う列の数, クラス, 学習の前に直すことの注意)
- **気付きから手順を足す**: 気付きに合う手順を足す (ID らしい列と定数の列を落とす, 欠損の多い列を埋める (数値は中央値, それ以外は最も多い値), 偏った分布の対数, 外れ値の切り詰め, 表記のゆれをそろえる (目的の列も), 同じ文を落とす, 空の文を除くなど). 画像, 文, 点群でも使える
- **学習できる形にする手順を作る**: 列の型から, 全ての列を数値にし欠損を無くす手順を作る (文, ID, 定数の列を落とす, 日時を分解, カテゴリをワンホットか番号付け, 欠損を埋める, 偏った数値の対数. 重複した行を落とし, 表記のゆれをそろえる. 時系列は, 数値の列 (目的の列も) の 1 つ前と, 自己相関で見つけた 1 周期前の値, 1 周期の移動平均の列を足し (店ごとのような複数の系列は, 系列を分ける列を符号化する前に `by` で系列ごとに. 系列を分ける列は, 値が 20 種類までならワンホット, それより多ければ番号付け), 過去が足りない始めの行を落とし, 時刻の列から曜日と月 (1 日より細かい間隔なら時と曜日) の列を足す. 最後に標準化)
- タスクを決めていないレシピは, 目的の列から推定したタスク (分類か回帰) で始める
- **異常の検知**: タスクの「異常の検知」(`anomaly`) を選ぶと, 分割と正解の欠けた行と行の id の列の欄が異常の検知の決まりになる (下の「15. 異常の検知の表の分析」)
- **効果を見積もる**: タスクの「効果を見積もる」(`uplift`) を選ぶと, 処置の列, 結果の種類, 行の id の列の欄を出し, 分割と正解の欠けた行の欄が効果を見積もるの決まりになる. 介入の記録の要約を前処理のタブに出す (下の「16. 介入の記録の表の分析」)
- **値段を変える判断**: タスクの「値段を変える判断」(`price`) を選ぶと, 値段の列, 原価の列, 商品の id の列, 行の id の列の欄を出し, 分割と正解の欠けた行の欄と手順の列の候補が値段を変える判断の決まりになる. 値段を変えた記録の要約を前処理のタブに出す (下の「17. 値段を変えた記録の表の分析」)
- **時間をまたぐ量の判断**: タスクの「時間をまたぐ量の判断」(`demand`) を選ぶと, 商品の id の列, 日付の列, 在庫の数の列, 先の期間の日数, 発注を決める日の間隔, 行の id の列の欄を出し, 分割と正解の欠けた行の欄と手順の列の候補が時間をまたぐ量の判断の決まりになる. 需要の記録の要約を前処理のタブに出す (下の「18. 需要の記録の表の分析」)
- **決めてほしいこと**: 自動では決めきれないことを, 前処理のタブの先頭に選択肢付きのカードで出す. 押すとそのまま反映する (読み方, 目的の列, レシピ). 選んだ結果で当てはまらなくなったもの (分割を変えた, 中身の手順を作ったなど) は消え, 「このまま」と, 条件では消せない選択 (リークの疑いの列を落とすか残すか. 目的の列ごと) はブラウザに覚えて次から出さない. 残っている数は書き出しの欄にも出す. 今のカード:
    - 目的の列が無い: 名前と型から候補の列を出す
    - Excel に他のシートがある (読み込みの設定でシートを選んでいない): このままか, 他のシートを読むか
    - 表の中に文の列がある: 表のままでは落とすので, 文として読むか, 落としてよいか (文として読むと, 学習に使うのは文と目的の列だけになる)
    - 目的の列とほぼ同じ列 (リークの疑い. 時刻や系列のような役割の列は除く): 落とすか残すか
    - 時系列や分類で分割が合わない (時系列なのに時刻の順でない, クラスが偏るのに層別でない): 合う分割にするか. 異常の検知は分割が無作為だけ, 効果を見積もると値段を変える判断は層化だけなので, どれも他の分割を勧めない. 時間をまたぐ量の判断は時刻の順だけなので, 時系列では時刻の順を勧める
    - 時刻に抜けがあり, 行でずらす過去の値の列を足している: 抜けを挟むと 1 周期前が暦の 1 周期前にならない. このままか, 日付でずらすか (ML-EDA の lag の `time` と `freq`. freq は分析の時刻の間隔. 月や年のような 28 日以上の間隔は長さが変わるので出さない), 過去の値の列を外すか. どちらが良いかはデータによるので, 勧めは「このまま」にし, 学習で比べることを促す
    - 画像, 文, 点群, 音声で中身の手順が無い: 分析から作るか
    - 文の区切り方が, ML-EDA が比べて勧めるもの (下) と違う: 勧めに変えるか, このままか
- **文の区切り方**: 文のデータは, ML-EDA の分析 (`items.tokenizers`) が見本の文で文字, 語, 部分語を比べた結果 (語彙の大きさ, 1 つの文のトークンの数, 語彙に無い語の割合, 勧める長さ) を中身の手順の欄に表で出す. 行の「使う」で vocabulary をその区切り方にする. 「学習用の配列にする手順を作る」は勧めた区切り方を使う
- **中身の手順** (画像, 文, 点群, 音声): 表の手順の後に, 1 件ずつの中身を同じ形の配列にする手順 (item_steps) を並べる. 「学習用の配列にする手順を作る」で分析の結果から作る (画像は最も多い大きさに resize, 色の形式が混ざれば rgb, normalize. 文は ML-EDA が比べて勧めた区切り方と長さの vocabulary (比べた結果が無ければ, 語数の第 3 四分位の 1.5 倍の長さ). 点群は点の数の中央値 (1024 まで) の sample_points と normalize_cloud. 音声は最も多い標本化の周波数の resample, 最も多いチャンネルの数の mix_channels, 長さの中央値 (0.01 秒に丸め, 30 秒まで) の fix_length (この順は ML-EDA の設計の順). 周波数などがそろっていても足す (推論で読む新しい 1 件も同じ形にするため. 画像の resize と同じ)). 選べる手順と引数の欄は ML-EDA の手順の登録簿 (`ITEM_STEPS`) の, その種類のもの (`GET /api/info` の `item_steps`). 読めない件があれば, 表の手順の先頭に filter_rows (画像は width が notna, 点群と音声などは error が isna) も足す. 画像などは, 中身を読まずに (`prepare(..., read_items=False)`) 中身の手順を確かめ, 読めない件や大きさ, 色の形式, 点の数, 音声の周波数とチャンネルと長さのばらつきの注意と分割の件数とクラスを出す (全ての中身は書き出しのときに読む). 写真のような大きな画像は長い辺を 224 までに縮め, 比べた結果が無い場合の空白で区切らない文は文字ごとの語彙にする. 中身の手順の引数の上限 (`STEP_LIMITS`) は, 手順を中身にかける全ての経路 (数件で試す (`item_preview`), 書き出し, 学習のプロジェクトへの書き出し, ファイルの組の書き出し) で, かける前に API で確かめ, 超えれば手順の番号と入れた値を添えて 422 で止める. 上限はバックエンドが持ち (`GET /api/info` の `item_steps` の `limits`), 版 1 の中身の手順の欄でも, 上限を超えた値に手順の番号と上限を添えた理由を出し, 「数件で試す」と書き出し (学習のプロジェクトへの書き出しも) を押せなくする (送る前に分かるように. ファイルの組の書き出しの欄と同じ). 同じ名前の引数は, どの手順でも同じ上限にする (手順ごとに覚えずに済むように). 上限は画像の辺 (`width`, `height`) が 4096 画素, 点の数 (`points`) が 100 万点, 音声の標本化の周波数 (`rate`) が 192000 Hz, 長さ (`seconds`) が 600 秒, チャンネルの数 (`channels`) が 32, 語彙の大きさ (`max_tokens`) と文の長さ (`length`) が 65536 (大きすぎる値で手元の計算機の記憶を使い切らないため. 192000 Hz は録音の機器の高い側の周波数. 両方が上限の 1 チャンネルの音声は 1 件で約 460 MB の 32 ビットの数になり, これより大きいと数件の見本 (8 件で約 3.7 GB) だけで手元の記憶を使い切りかねない). 600 秒より長い録音は, 前もって 600 秒以下のファイルに分けてから読み込む. 入力が長い音声は, `fix_length` を `resample` の前に置くと, 周波数を変える前に短くするので記憶を減らせる
- **中身の手順の前と後** (画像, 文, 点群, 音声): 「数件で試す」で, 学習用の少ない見本 (100 件) で当てはめた中身の手順を, 学習用から選んだ 8 件にかけた前と後を出す (`POST /api/sources/{id}/item_preview`. ML-EDA の `preview_items`). 画像は並べ, 文は語に戻した番号の並び, 点群は 2 つの 3D 表示, 音声は選んだ 1 件の前と後の再生と波形 (どちらも先頭の 5 秒. 何件も返すので「中身を見る」より短く. 再生用の音は WAVE の data URL で返す. 後の周波数は最後の resample の rate)
- 画像, 文, 点群, 音声のディレクトリは, クラスのフォルダの名前の label を目的の列にして登録する
- 書き出すと, ML-Found の学習スクリプトで読み込む例と, モデルを組むときの数 (1 件の入力の形と型, 出力の幅 (目的の無いデータセットでは出さない), 文の語彙の大きさ (埋め込みの数. ML-EDA が書き出したレシピの最後の `vocabulary` から求める) は ML-EDA の `model_inputs` から. 書き出しの API の `hints`) を出す. ML-CreateArchitecture のモデルとは自動でつながないので, 部品の引数に合わせる数を示す

## 11. 問題から始める

問題の設定の段階 (ML-Quest と画面の ML-Pathfinder) で決めたことを入れた状態で始め, ここで変えた選び方を問題に書き戻す (段階どうしのつなぎ目の誤りを早く見つけるため). 「データを登録」から入れる流れも使える.

- **始める**: データの画面の「問題から始める」で `problem.yaml` (か, それを持つディレクトリ) を選ぶ. 殻で問題を選んでいれば, データの一覧の上の「この問題から始める」でも同じように始める (上の「3. 画面」の「殻で選んだ問題」). ML-Quest の `recipe_from` で, データの場所と読み方 (問題に入れたデータ. 写しが消えていれば元の場所) と, レシピの雛形 (目的の列, タスク, 使わない列を落とす手順, 時系列なら決める時点で分かる期からの系列ごとの過去の値, 分割と, あれば相手をまとめるグループの列) を受け取り, データを登録してレシピを保存する (列の予測. 画像か表の生成とファイルの組の受け持ちは下の「受け持ち」). 問題の場所と, `recipe_from` の知らせ (`notes`) は登録したデータに持つ (`problem`, `problem_notes`). 知らせは「問題」のカードの「始めたときの知らせ」に出し続ける (始めた後に直すことを, 前処理を組み立てる間に見られるように). 問題を渡せない (直すところがある) か, データを入れていなければ, 理由を出して登録しない
- **食い違いを見る**: 問題から始めたデータでは, 前処理のタブの先頭に「問題」のカードを出す. 編集中のレシピを ML-Quest の `apply_recipe` で試しに書き戻し (保存はしない), 変わる点 (目的の列, タスク), 食い違い (使ってはいけない列を使う (誤り), 決める時点で分からない期の過去の値, 相手をまとめる列とレシピのグループの列の違い, 時系列なのに時刻の順でない分割 (注意)), 選ぶ問い (予測の時点で分からない列をレシピで使っている: 分かる列に移すか, レシピで落とすか) を出す. まとめるで学習する受け持ちの問題から始めたデータは, 確かめをせず, カードにレシピを持たない理由を誤りでなく案内として出し, 群分けのタブへのリンクを置く (下の「14. 群分けの表の分析」)
- **書き戻す**: 選ぶ問いに全て答え, 誤りの食い違いが無ければ「問題に書き戻す」を押せる. ML-Quest の `apply_recipe` と `resolve_choice` で問題を直して元の場所に保存し (レシピも問題の `data.recipe` に持つ), 落とすと選んだ列を足したレシピをここにも保存する. 列の使い方は方針なので, 自動では変えず必ず選ばせる
- **問題の一覧**: 「問題から始める」の上に, ML-Pathfinder の置き場 (上の「6. 置き場」) にある問題を, 更新の新しい順に並べる (名前, 場所, 更新時刻). 押すとその問題を選ぶ. 始められないもの (列の予測, 画像か表の生成, ファイルの組の受け持ち, 異常の検知, 効果の見積もり, 値段を変える判断, 時間をまたぐ量の判断, 並べるかまとめるで学習する受け持ちのどれでもない, 列の予測か画像か表の生成か異常の検知か効果の見積もりか値段を変える判断か時間をまたぐ量の判断か並べるかまとめるでデータを入れていない, 値段を変える判断か時間をまたぐ量の判断を受けない版の ML-Quest, 並べるかまとめるで骨組みを書き出せない, 読めない) も理由を付けて並べる (黙って消さない). 置き場の外のものは, 下のファイルの選び方で選ぶ
- **学習のプロジェクトへ書き出す**: 始めた問題に ML-Quest の学習のプロジェクトの記録 (`project.dataset`. 学習のスクリプトがデータセットを読む場所) があれば, 書き出しの欄に「学習のプロジェクトへ書き出す」を出す. 書き出し先は記録のまま (名前を選ばない). 学習のプロジェクトへ手でファイルを写さずに渡すため
    - 書き出し先に前に書き出したデータセットがあれば, 上書きしてよいかを確かめてから上書きる. データセットでないもの (`dataset.yaml` の無いディレクトリやファイル) は上書きしない (ML-EDA の書き出しの決まりと同じ)
    - 記録の `project.path` と `project.dataset` は絶対パスで, 両方が要る. 学習のプロジェクトのディレクトリ (`project.path`) が無ければ書き出さない (消したか動かした学習のプロジェクトの場所に作らないように). 書き出し先は学習のプロジェクトの中に限る. 外の絶対パス, `..` で外に出る場所, 途中のシンボリックリンクをたどると外に出る場所と, 学習のプロジェクトのディレクトリそのものは, 上書きの印を付けても理由を付けて 422 で断る (ML-Quest の骨組みは書き出し先を学習のプロジェクトの中の `outputs` か `data` に置くので, 外を指すのは手で書き換えた記録. 問題のファイルの書き換えで, 手元の思わぬファイルを上書きしないため). 中の親のディレクトリは無ければ作る. 書き出し先がシンボリックリンクなら, 先がデータセットでも上書きしない. これらの確かめは書き出しと同じ鍵の中で行う
    - 記録が無い問題 (学習のプロジェクトをまだ作っていない) では, ボタンの代わりに「問題の設定の段階で学習のプロジェクトを書き出してください」と出す
    - 書き出すとレシピも保存し, 書き出した場所を登録したデータに持つ (データセットの一覧に並べるため). 結果はいつもの書き出しと同じく, 場所とモデルを組むときの数を出す
- 問題のファイルが消えたか読めなければ, カードに理由を出す (データの分析は続けられる)
- 問題のファイルであること (名前と作った時刻を持つ) と, 始めたときと同じ問題 (作った時刻が同じ) であることを確かめてから読み書きする (レシピなど別の YAML を上書きしないように). 書き戻すときは, 確かめたときのファイルの中身の印 (sha256. 必須) を送り返し, 読む前と保存の直前に比べて, 違えば (ML-Pathfinder などで変えた) 書き戻さない (画面は確かめ直す). 書き戻した問題が後ろの段階に渡せること (ML-Quest の `handoff`) と, できたレシピを前処理にかけられることも確かめる
- 画面は, 確かめが最新の編集に追いつくまで書き戻しを押せないようにし, 書き戻すのは待つ前の最新のレシピ
- **問題の版**: ML-Quest の問題の版 1 と版 2 を読む. 版 1 は ML-Quest の `load_problem` が読んだ後に版 2 に移す (`upgrade_problem`) ので, この画面は版 2 だけを扱う. 書き戻すと版 2 で保存する (ML-Quest の `save_problem`. ファイルは書き戻すまで版 1 のまま). 食い違いの場所は版 2 の名前 (`ml.parts.0.available_lag` など)
- **受け持ち**: 始めるのと書き戻しは, 列の予測 (受け持ちが予測する (`predict`) で, 正解の種類が表の列 (`column`)) と, 画像か表の生成 (作る (`generate`) で, 正解の種類が画像 (`image`) か表 (`table`)) と, ファイルの組の受け持ち (予測するで, 正解の種類が画像の領域 (`mask`) か点群 (`point_cloud`)) と, 異常の検知 (予測するで, 正解の種類が異常 (`anomaly`), 作り方が既製のモデルをそのままでない. 下の「15. 異常の検知の表の分析」) と, 効果の見積もり (効果を見積もる (`effect`) で, 方策でなく (`autonomous` が真でない), 今ある記録から集め (`collect: log`), 作り方が既製のモデルをそのままでなく, 記録で変えたもの (`varied`) が値段でない. 下の「16. 介入の記録の表の分析」) と, 値段を変える判断 (効果の見積もりと同じく今ある記録から学び, 記録で変えたものが値段 (`varied: price`). 下の「17. 値段を変えた記録の表の分析」) と, 時間をまたぐ量の判断 (予測するで, 正解の種類が先の期間の需要 (`demand`), 作り方が既製のモデルをそのままでない. 下の「18. 需要の記録の表の分析」) (ML-Quest の `recipe_from` と `apply_recipe` と同じ). 並べるで学習する受け持ち (並べる (`rank`) で, 作り方が既製のモデルをそのまま (`pretrained`) でない. ML-Quest の並べるの骨組みと同じ決まり) は始めることだけで, 書き戻しは無い (下の「13. 並べるの反応の表の分析」). まとめるで学習する受け持ち (まとめる (`group`) で, 作り方が既製のモデルをそのままでない. ML-Quest のまとめるの骨組みと同じ決まり) はレシピを持たず, 群分けのタブの選び方を ML-Quest の `apply_group` で書き戻す (下の「14. 群分けの表の分析」). 受け持ちの見分けは ML-Quest の公開の関数 (`is_column_part`, `is_items_part`, `active_value`) で行う (異常の検知は `active_value` の受け持ち, 正解の種類, 作り方の答えで見分ける. ML-Quest の `is_anomaly_part` と同じ決まり. 効果の見積もりと値段を変える判断も同じく, ML-Quest の `is_uplift_part` と `is_price_part` と同じ決まりで見分ける. 時間をまたぐ量の判断は ML-Quest の `skeleton_type` が `demand` を返すかで見分ける. 書き出す骨組みの型を ML-Quest が決めるので, 決まりを写して持たずに済むため). 他の受け持ち (方策で効果を見積もるなど) と正解の種類 (文など), 既製のモデルをそのまま使う予測と並べるとまとめるの問題は, 使えない受け持ちと正解の種類 (画面の選択肢と同じ言葉と値. 「効果を見積もる」(effect) と方策など), 使えない理由 (方策は環境とのやり取りで集めるのでデータの分析の段階を通らない, など), 使える受け持ち, 「データを登録から入れて分析できる」ことを 422 で返す (画面は理由を出す). 始めた後に問題の受け持ちが変わった場合の確かめと書き戻しも同じ
- **画像か表の生成**: 目的の列が無いので, 列の予測と同じく入れたデータを登録し, ML-Quest の雛形の目的の列の無いレシピ (`task: none`, 手順は空, 無作為の分割) を保存する. 登録する前に, データの種類 (ML-EDA の読み込んだデータの `kind`) が作るものに合うこと (画像は `image`, 表は `table` か `timeseries`. 日時の列を見つけた表は `timeseries` になるが, 中身は表のため) を確かめ, 合わなければ作るものとデータの種類の文を 422 で返して登録しない. 食い違いの確かめと書き戻しと「学習のプロジェクトへ書き出す」は列の予測と同じ流れで, 書き戻すとレシピ (画像の中身の手順 `item_steps` も) を問題の `data.recipe` に持つ. ML-Quest の骨組みは, 学習のプロジェクトの記録の場所 (config の `data.dataset`) から, 目的の列の無い版 1 のデータセット (種類が `image` か `table`, 検証用の分割付き. 表は学習に使う列に欠損が無いこと) を読むので, 書き出しはその形になる (目的の列を書いたレシピと, 検証用の分割の無いレシピは, ML-Quest の食い違いとしてカードに出す)
    - 画像の生成は, ファイルの組の書き出しの画面を使わない. 骨組みが読むのは画像のディレクトリを `image_folder` で読んだ版 1 のデータセットで, ファイルの組の書き出し (版 2 と版 3) は正解のディレクトリと組にした別の形のため. 大きさをそろえる `resize` などの中身の手順は, 前処理のタブのレシピの中身の手順で選ぶ
- **ファイルの組の受け持ち**: データを登録せず (正解が表の列でなく, 版 2 の書き出しは登録したデータとレシピを通さないため), ファイルの組の書き出しの画面 (上の「9. ファイルの組の書き出し」) に問題の場所を付けて移る. データを入れていない問題も始められる (ディレクトリは画面で選ぶ). 画面を開くたびに問題を読み直し, 下書き (書き戻した設定があればそれ) で欄を埋める
    - 書き出しは, 確かめたときの問題の中身の印を送り返し, 書き出す前に比べる. 書き出しの設定の形の誤りは 422, ML-Quest の食い違いの誤り (正解の種類に合わない書き出し, グループの無いグループごとの分割) は 409 で書き出さない. 入力と正解のディレクトリが無ければ 422
    - 書き出した後, 保存の直前にもう一度中身の印を比べ, 違えば (ML-Pathfinder などで変えた) 書き戻さずに 409 で「書き出したが書き戻していない」と返す (画面は開き直して書き出し直す)

## 12. 記録した軌跡の分析

強化学習の方策を走らせた軌跡 (ML-Found の評価の軌跡と, 同じ列を持つ手元の表) を, 登録したデータの 1 つとして分析する. 読み込みと要約は ML-EDA の `load_trajectory` と `describe_trajectory` が行い, このアプリは要約を画面に並べて書き出すだけを受け持つ (表の分析と同じく, 分析の仕組みを ML-EDA に置くため).

- **登録**: 「データを登録」で選んだファイル (表 `.csv`, `.parquet` か説明 `.json`) が `load_trajectory` で読めれば, 読み込みの候補の先頭に `trajectory` (種類 `trajectory`) を足す (軌跡の表は普通の表としても読めるので, 表の候補も残す). 読む前に見出しだけを確かめ, 合わなければ読まずに候補から外す (軌跡でない大きなファイルを, 候補を出すためだけに全て読まないように). CSV は 1 行目, Parquet はスキーマ (pyarrow) の列の名前に `episode` と `step` があるか, JSON は先頭 (64 KiB) が辞書で `format_version` と `file` の鍵を含むか. 候補を出すときに読んだ要約は覚えて, 登録と画面でそのまま使う (同じファイルを何度も読まないように). 同じ軌跡を表 (`foo.csv`) と説明 (`foo.json`) の両方から登録してもよい (別のデータとして並ぶ. 中身は同じ要約) 読み込みの設定と目的の列は持たない. 登録するときに読めることを確かめ, 読めなければ ML-EDA の理由を 422 で返す
- **読み直し**: 要約は, 登録した場所と, 同じ名前の `.csv`, `.parquet`, `.json` の更新時刻ごとにメモリに覚える (表を登録した後に隣の説明を書き換えても読み直すように)
- **表の分析は使わない**: 軌跡のデータには, データを表として読む API (分析, 表の中身, 前処理の前と後, 書き出しなど) は 422 を返し, 画面もそれらのタブを出さない (`load_data` は軌跡を普通の表として読み, 守りで止めた行の空と nan を分けないため)
- **画面**: データごとの画面で, 表のタブの代わりに次のタブを出す. 値は全て `describe_trajectory` の結果をそのまま使う
    - **概要と気付き**: エピソード, 行, 環境を進めた歩数, 長さと報酬の和の平均, 守りの有無, 行動を選んだ確率の列の有無. 読むときと要約で気付いたこと (`notes`). エピソードの長さと報酬の和の要約 (平均, 標準偏差, 最小, 中央値, 最大. 全てのエピソードで求めたもの) とヒストグラム (`per_episode` から描く. 切った場合は先頭の 1000 件で描いたと添える. 区間は値の数の平方根 (20 まで) の同じ幅で, 値の範囲 (最大 - 最小 + 1) が 20 以下の整数は 1 つの値を 1 つの区間にし, 区間の見出しを値にする. 全て同じ値なら範囲を ±0.5 に広げる), 和が有限でないエピソードの数 (`unknown_returns`), 終わり方ごとのエピソードの数 (`ends`), 説明の項目 (出どころ (`source`. ML-Found の書いた英字の名前でなく, 評価の loader, 守り付きの評価のような日本語の言い換えで出す. 知らない値はそのまま), 環境, エポック, 観測と行動の空間など) と, 観測, 行動, その他の列 (`extra_columns`)
    - **観測と行動**: 要素ごとの欠け (`missing`), nan (数でない値), 無限大の数と, 有限の値の最小, 最大, 平均, 標準偏差, 中央値. 欠けは ML-EDA の `missing` を出す (nan は値で, 欠けと分けて数えるため). 値ごとの数 (`counts`. 整数の列で異なる値が 50 以下) のある行動は横棒グラフで描く (Discrete の行動の偏り). 他 (Box の行動) は要素ごとの統計だけ. 行動を選んだ確率の列 (`action_prob`. ML-EDA の `with_action_prob` と `action_prob`) があれば, 欠けの数, 範囲 (0 より大きく 1 以下) の外の数と, 範囲の中の値の最小, 最大, 平均, 中央値. 無ければ無いと出す
    - **守り** (守りの列のある表だけ): 結果ごとの行の数の横棒グラフ (結果は英字でなく日本語の名前で出す: そのまま通した, 範囲に収めた, 代わりの行動にした, 止めた, 引き継いだ, 空. 知らない結果は「その他 (値)」) と, 働いた理由ごとの行の数の表 (多い順)
    - **エピソード**: エピソードごとの行の数, 長さ, 報酬の和, 終わり方, 乱数の種 (`per_episode`). エピソードが 1000 件を超えて切った場合 (`per_episode_truncated`) は, 全ての数と並べた数を添えて知らせる
- **書き出し**: 「分析を書き出す」で, 要約をそのまま JSON (`<軌跡の名前>.analysis.json`. 名前のパスに使えない文字は `_` に) としてブラウザで保存する. 置き場には書かない (データセットではなく, 元のデータの読み直しで同じ要約を作れるため)

## 13. 並べるの反応の表の分析

並べる (推薦) の問題に入れた反応の表を, 問題で答えた列 (ML-Quest の `ml.parts.<n>.rank` の `user`, `item`, `time`, `reaction`) で読み, 偏りと除く行を見てから, 並べるの骨組みが読む場所に写す. 読み込みと要約は ML-EDA の `load_reactions` と `describe_reactions` が行い, このアプリは要約を画面に並べて写すだけを受け持つ (除く行の決まりを ML-EDA と ML-Quest の骨組みにそろえ, 画面の数と学習の `train.log` の数を合わせるため).

- **始める**: 「問題から始める」で並べるで学習する問題を選ぶと, 入れた反応の表 (写しが消えていれば元の場所) を, 問題の手元のデータの読み方 (`data.loader` と `data.options`. 読み込みが無ければ ML-EDA の候補の先頭) で読み, 種類 `reactions` のデータとして登録する (骨組みの学習のスクリプトと同じ読み方にするため). ML-Quest の `recipe_from` は並べるを扱わないので使わず, レシピも保存しない. ML-Quest の `project_error` で骨組みを書き出せない (出力の形が順位でない, 入れたデータが表でない, 直すところがある) か, データを入れていないか, 反応の表がファイル 1 つでないか, 問題の列で反応の表として読めない (列が無い, 時刻が数でも日時でもない) 場合は, 理由を 422 で返して登録しない. 一覧の始められるかと理由も同じ確かめ
- **要約**: 要約を出すたびに問題を読み直し, その列で, 読み込み済みの表 (`Data`) を `load_reactions` に渡す (読み直さない). 始めた後に受け持ちが並べるでなくなった場合と, 答え直した列が表に無い場合は 422
- **表の分析とレシピは使わない**: 反応の表の画面は表の分析のタブを出さず, レシピの確かめ, 書き戻し, レシピでの書き出し (`export_project`) は 422 で断る. 並べるは反応の表をデータセットにせず, 分割は骨組みが時刻で行うため (ML-EDA の「並べるの反応の表」の「分割は持たない」)
- **画面**: データごとの画面で, 表のタブの代わりに次のタブを出す. 値は全て `describe_reactions` の結果をそのまま使う
    - **概要と気付き**: 反応 (除いた後の行), 除く前の行, 除いた行, 利用者, 品物, 利用者と品物の組の数, 密度, 並べる件数 (K). 読むときと要約で気付いたこと (`notes`). 読んだ列 (反応の強さの列が無ければ全ての行を反応とみなすこと), 除いた行の内訳 (欠け, そのうち日時として読めない時刻, 強さが 0 以下か数でない), 時刻の種類 (数か日時) と範囲と異なる時刻の数, 反応の強さの要約 (列があれば)
    - **偏り**: 品物の人気の偏り (上位 10% の品物の数とその反応の割合, ジニ係数, 同じ組の 2 行目からの数) と, 反応の多い品物の先頭 10 件の表. 利用者ごとと品物ごとの反応の数の要約 (平均, 標準偏差, 最小, 中央値, 最大, 1 回だけの数) と, 区切りごとの数の横棒グラフ
    - **表の中身**: 表の中身のタブと同じ (元の表のまま)
    - **書き出し**: 下
- **学習のプロジェクトへ書き出す**: 反応の表を前処理せず, ファイル 1 つのまま, 問題の学習のプロジェクトの記録の書き出し先 (`project.dataset`. ML-Quest の骨組みの config の `data.dataset` で, データを入れた問題では `data/` の写し) に写す. 骨組みは問題の読み方で `load_data` で読み, 時刻で分ける
    - 写す前に, 今の問題の列で反応の表として読めることを確かめ, 結果に骨組みが反応とみなす行の数と除く行の数を添える
    - 書き出し先に前に置いたファイルがあれば, 上書きしてよいかを確かめてから上書きる (骨組みを作ると入れたデータを写すので, 初めから置いてあることが多い). ファイルでないもの (ディレクトリ, シンボリックリンク) は上書きしない. 書き出し先と反応の表の拡張子が違えば写さない (読み込みを決めていない読み方は拡張子で候補が変わるため). 書き出し先が登録した表そのものなら写さない
    - 写すのは同じディレクトリの一時ファイルに写してから置き換える (途中で止まっても前のファイルを壊さないように). 記録と学習のプロジェクトの確かめ (上の「11. 問題から始める」の「学習のプロジェクトへ書き出す」) と上書きしてよいかの確かめは, 写しと同じ鍵の中で行う
    - 書き出したファイルはデータセットではないので, データセットの一覧には並ばない

## 14. 群分けの表の分析

群分け (まとめる) の課題の, 正解の無い 1 行が 1 つの対象の表 (客, 店, 品物など) を, 登録した表のまま分析し, 学習に通さずに群を作って群の要約を見てから, 学習のプロジェクトへ表のファイルを渡す. 書き出しは 2 つあり, カードの名前と説明の文で使い分けを示す. 学習のプロジェクトへ渡すのは「学習のプロジェクトへ書き出す」(表のファイル. ML-Quest のまとめるの骨組みが `load_data` で読む形) だけ. 「群分けの表を分析用に書き出す」(版 2) は分析の保存 (読み直して群の要約を求める) で, 骨組みは読まない (ML-Quest のまとめるの骨組みは, 並べるの骨組みと同じく表のファイルを `load_data` で読み, 分割も骨組みが行うため. ML-EDA の「群分けの表」の決まり). カードの説明は初めての利用者に向け, 何のための書き出しかと, 学習には「学習のプロジェクトへ書き出す」を使うことを先に書く. 群の要約と書き出しは ML-EDA の `describe_groups` と `export_group_rows` が行い, このアプリは列と群の数を選ぶ画面と, 要約を並べる表だけを受け持つ (群の作り方と要約の形を ML-EDA と ML-Quest のまとめるの骨組みにそろえ, 分析の段階の群と学習の後の群を同じ表で比べられるようにするため).

- **どのデータで**: 種類が表か時系列のデータ (ML-EDA の `describe_groups` が読むもの). データごとの画面の「群分け」のタブで行う. 表の分析 (概要, 列, 関係など) はそのまま使える. 読み込み済みの表 (`Data`) を渡し, 読み直さない
- **群を作る列**: 列の一覧から選ぶ. 初めは, 型が ID, 文, 日時, 定数, 空の列と目的の列を外した列を選ぶ (行を見分ける列や値が 1 つの列は群を作る力が無く, 文と日時は別の扱いが要るため. 外した列も選べる). 1 つ以上選ばなければ作れない
- **群の数と乱数の種**: 群の数は 2 から 50 の整数 (k-means を置き方を変えて繰り返し, 作り直して安定性も数えるので, 大きな数で手元の計算機を長く使わないように. 上限は画面と API の両方で確かめ, 同じ値を両方に持つ). 乱数の種は 0 以上の整数 (既定 0)
- **安定性の数え方**: 問題から始めたデータでは, 問題の答え (`group.stability`) の数え方で数える (種を変える `seed` か, 標本を変える `sample`. ML-EDA の `describe_groups` の `stability`). 問題から始めないデータ, 答えていない場合, まとめるでなくなった場合と, 問題を読めない場合 (読み直しが失敗した場合も, 前に読んだ答えを使わない) は `seed`. 問題を読み直している間は, 古い答えの数え方で作らないように「群を作る」を押せず, 理由を出す. 引く割合 (`fraction`) は問題に答えが無いので送らず, ML-EDA の既定 (骨組みの config の `group.fraction` の既定と同じ 0.8) を使う. タブでは選ばない (骨組みは問題の答えで数えるので, 選べると答えと違う数え方の値を骨組みと比べてしまうため. 欄と答えの違いの知らせと書き戻しも, 数え方を扱わない). 答えが変わると欄と同じく群の要約を消す
- **群の要約**: 群の数, 行, 調整ランド指数 (作り直した群との一致の平均と最も低い回), シルエット係数 (群のまとまり) と, 2 つの指標の意味 (調整ランド指数は, 返した数え方 (`stability.method`) に合わせて, 種を変えて作り直したか, 種を変えて行の一部 (`stability.fraction` の割合) を引き直して作り直したかを出し, 1 で全く同じ分かれ方, 0 で偶然と同じ程度. シルエット係数は -1 から 1 で, 1 に近いほど同じ群の行どうしが近い). 気付き (`notes`). 群の要約の表 (群, 行, 割合, 安定性 (Jaccard 係数の平均) と群を作った列ごとの平均か最も多い値. 最後に全体の行). 群を作った列 (数の列と種類の列の分け方), そろえた後の列の数, 乱数の種. 群の番号は ML-EDA の番号 (0 から) のまま「群 0」のように出す (学習の後の群の要約と同じ番号で比べるため). 内部の英字の名前 (`kmeans` など) は出さない
- **選び方を変えたら**: 列, 群の数, 乱数の種を変えると, 前の群の要約を消す (どの選び方の群かを取り違えないように)
- **群分けの表を分析用に書き出す**: 分析の保存で, 学習には使わない (カードの説明に, 学習のプロジェクトへは「学習のプロジェクトへ書き出す」で表のファイルを渡すと書く). 群を作る列 (群の要約と同じ選び方) と, 行を見分ける列 (任意. 群を作る列の他から選ぶ. 選んだ後でその列を群を作る列に入れると「なし」に戻し, 送る値も見せる値にそろえる. 無ければ行の位置) を, 置き場の `datasets` の下に版 2 で書き出す (`export_group_rows`). 群の数は書かない (群の要約を求めるときに決める). 分割は無作為 (学習用と検証用. 検証用の割合を選べる. 既定 2 割) か分けない. 版 1 の書き出しと同じく, データセットの名前と「同じ名前があれば上書きする」を持ち, 書き出しはアプリの中で 1 つずつ行う. 結果に, 書き出した場所, 書き出しの注意 (ML-EDA の `notes`), `load_items` で読み直して `describe_groups` で群の要約を求める例 (群の数は書き出したときの値) を出す. 上の群を作る列か群の数を変えると, 書き出しの結果を消す. 書き出したものはデータセットの一覧に版 2 の群分けの表として並ぶ
- **問題から始める**: 「問題から始める」でまとめるで学習する問題を選ぶと, 入れた表 (写しが消えていれば元の場所) を, 問題の手元のデータの読み方 (`data.loader` と `data.options`) で読んで登録し, 群分けのタブを開く (骨組みの学習のスクリプトと同じ読み方にするため). 種類は読み込みのまま (表か時系列) で, 表の分析のタブもそのまま使える. 目的の列は持たない. ML-Quest の `recipe_from` はまとめるを扱わないので使わず, レシピも保存しない (群分けは表をデータセットにせず, 分割は骨組みが行うため). レシピの確かめ, 書き戻し, レシピでの書き出しは 422 で断る. ML-Quest の `project_error` で骨組みを書き出せない (出力の形が群でない, 入れたデータが表でない, 直すところがある) か, データを入れていないか, 表がファイル 1 つでないか, 表か時系列として読めないか, 答えた群を作る列か行を見分ける列が表に無いか, 骨組みが使えない名前 (下の「学習のプロジェクトへ書き出す」) の場合は, 理由を 422 で返して登録しない. 一覧の始められるかと理由も, 読む前に分かる確かめ (骨組みを書き出せるか, データを入れたか) は同じ
- **問題の答え**: 群分けのタブは, 開くたびに問題を読み直し, 群を作る列, 行を見分ける列, 群の数を問題の答え (ML-Quest の `ml.parts.<n>.group`) で埋める (表に無い列は外し, 範囲の外の群の数はそのまま出して理由を出す). 問題のカードに名前と場所と答え (安定性の数え方も) を出し, 欄 (群を作る列, 行を見分ける列, 群の数) を答えと違う選び方にすると, 骨組みは問題の答えで群を作ることを知らせ, 下の「問題に書き戻す」を出す. 行を見分ける列の欄は「群分けの表を分析用に書き出す」の欄と同じもの (書き出しと書き戻しで行の見分け方を取り違えないため). 安定性の数え方が標本を変える (`sample`) なら, ここの調整ランド指数も標本を変えて数えることと, 骨組みは学習用の行から引くがここは全ての行から引くことを添える (分析の段階では学習用と検証用に分けないため). 始めた後に受け持ちがまとめるでなくなった場合は, 答えで埋めず, カードにそう出す
- **問題に書き戻す**: 欄が答えと違う間, 問題のカードで, 欄の選び方 (群を作る列, 行を見分ける列 (「なし」は外す), 群の数) を ML-Quest の `apply_group` で試しに書き戻し (`group_problem/check`. 保存はしない), 書き戻すと変わる点 (ML-Quest の変えた点の文. 書き出した学習のプロジェクトがあれば, 骨組みを書き出し直す案内も) を出す. 安定性の数え方はタブで選ばないので送らない (書いた鍵だけが書き戻るため). 「問題に書き戻す」で, 確かめたときの中身の印とともに書き戻して `save_problem` で保存し (`group_problem/write`), 問題を読み直す (前処理のタブのレシピの書き戻しと同じ流れ). 読み直した答えは欄と同じなので知らせと書き戻しは消え, 欄と群の要約はそのまま残す (自分の書き戻しで欄を埋め直さないため). `apply_group` が断る選び方 (骨組みを組めない名前, 群を作る列と行を見分ける列の重なり, 使えるデータに無い列など) は, 書き戻さずに理由を付けて 422 で返し, 画面はその理由を出す. 確かめた後に問題が他で変わっていれば 409 で断って確かめ直す. 書き出した学習のプロジェクトの config は変わらないので, 書き戻した後は ML-Pathfinder で骨組みを書き出し直す
- **前処理のタブ**: まとめるで学習する問題から始めたデータでも前処理のタブは開けるが, 「問題」のカードは確かめ (`problem/check`) をせず, レシピを持たない理由 (骨組みは表をファイル 1 つのまま読み, 分割も骨組みが行う) を案内として出し, 群分けのタブへのリンクを置く. 「学習のプロジェクトへ書き出す」も出さない (学習のプロジェクトへは群分けのタブから写すため). 受け持ちは, 開くたびに `GET /api/sources/{id}/group_problem` の答え (`group`) の有無で見分ける (始めた後に答え直しても合うように). 前に読んだ答えは使わず, 読み終えるまでと読み直す間 (画面に戻ったときなど) は, 確かめのカードと「学習のプロジェクトへ書き出す」を出さず, 確かめも呼ばない (前の答えのまま確かめの 422 を出さないため). 読めなければ, 今までどおり確かめのカードが理由を出す. 確かめの API の 422 は, レシピを送る呼び手への守りとして残す (分ける所を画面にし, API の約束を変えないため). 並べるの問題から始めたデータは種類が反応の表で, 前処理のタブを出さないので当たらない
- **学習のプロジェクトへ書き出す**: 表を前処理せず, ファイル 1 つのまま, 問題の学習のプロジェクトの記録の書き出し先 (`project.dataset`. ML-Quest の骨組みの config の `data.dataset` で, データを入れた問題では `data/` の写し) に写す. 骨組みは問題の読み方で `load_data` で読み, 群を作る列と行を見分ける列だけを使い, 学習用と検証用に無作為に分ける. 学習のプロジェクトへ渡すのはこの書き出しだけで, カードの説明にそう書く. 版 2 の群分けの表 (上の「群分けの表を分析用に書き出す」) は分析の保存で骨組みが読む形でないので, 学習のプロジェクトへは書き出さない
    - 写す前に, 今の問題の答えの列が表にあり, 群を作る列の名前が ML-Quest の `GROUP_TAKEN` (群の要約の鍵と 1 件の決まった鍵. `group`, `rows`, `share`, `stability`, `id`, `split`) に無く, 行を見分ける列の名前が `GROUP_ASSIGNED` (群の割り当ての表の他の列. `group`, `split`) に無いことを確かめ, 始めるときと同じ ML-Quest の確かめ (`project_error`) に誤りが無いことも確かめる (骨組みが止める誤りを先に出すため. 始めた後に行を見分ける列を群を作る列にも答え直した場合なども写さない. 名前の組は ML-Quest の公開の名前を使い, このアプリに持たない). 断る文は, 群の要約の列と 1 件の行の決まった列を分けて出し, 名前を変えた表を入れ直すか ML-Pathfinder で別の列を答え直すよう添える. 断った場合は前に写した表を残す. 結果に, 写した場所, 行の数, 骨組みが読む列を添える
    - 書き出し先の決まり (上書きしてよいかの確かめ, ファイルでないものは上書きしない, 拡張子が違えば写さない, 書き出し先が登録した表そのものなら写さない, 一時ファイルに写してから置き換える, 記録と学習のプロジェクトの確かめを写しと同じ鍵の中で行う) は並べるの反応の表と同じ (上の「13. 並べるの反応の表の分析」)
    - 書き出したファイルはデータセットではないので, データセットの一覧には並ばない
- **誤り**: 無い列, 同じ列を 2 回, 群を作るのに使えない名前の列 (ML-Quest の `GROUP_TAKEN` と同じ組. 群の要約の鍵と 1 件の行の決まった鍵の `id`, `split`), 群の数が行の数より多い, そろえた後の列の数が上限を超える, 行を見分ける列に欠けか同じ値がある場合などは, ML-EDA の理由を 422 で返して画面に出す

## 15. 異常の検知の表の分析

正常の行が多く, 異常の正解が無いか少しだけある表を, 登録した表のまま分析し, 正常の行だけで学ぶ異常の検知のデータセットを版 1 の `task: anomaly` で書き出す (ML-EDA の「異常の検知の表」). 分け方と数え方は ML-EDA の `prepare` と `export_dataset` が行い, このアプリはレシピの欄と, ML-EDA が返す数を並べるだけを受け持つ (学習用を正常の行に絞る決まりと数を, ML-EDA と ML-Quest の異常の検知の骨組みにそろえるため).

- **どのデータで**: 種類が表か時系列のデータ (ML-EDA が他の種類の異常の検知を誤りにするため). 他の種類ではタスクの「異常の検知」を選べない (選んだまま残れば ML-EDA の誤りを試した結果の所に出す)
- **目的の列**: 異常の正解の列 (異常は 1 か真, 正常は 0 か偽). 上の目的の列の欄で選ぶ. 正解の無い表は目的の列を選ばない (全ての行を正常と見なす). 他の値の列は ML-EDA の誤りを出す
- **分割**: 無作為だけ (正常の行を無作為に学習用, 検証用, テスト用に分け, 異常の行を検証用とテスト用に配る. ML-EDA の決まり). 他の分け方は選べず, 残っていれば欄の下に誤りを出す. 検証用とテスト用の割合は上の欄で選ぶ
- **正解の欠けた行**: 落とす, unlabeled の分割に残すに, 「正常と見なす」(`split.unlabeled: normal`. 異常の行にだけ印を付けた表のため) を足す. 正常と見なすは異常の検知だけで選べる
- **行の id の列**: 1 行ごとの番号 (ID) の列 (レシピの `id`. 度合いを出した行を元の表の行や人の確認の記録と突き合わせるため). 任意で, 「なし」なら ML-EDA が行の順番の番号の列 `row_id` を置く. 選んだ列は学習に使う列から除かれる (ML-EDA の決まり). 候補は, 分析で欠けも同じ値も無い列だけ (ML-EDA が他の列を誤りにするため. 前に選んだ列は候補でなくても出す). 目的の列は選べない
- **タスクを変えたら**: 異常の検知から他のタスクに変えると, 行の id の列と「正常と見なす」を消す (ML-EDA が他のタスクで誤りにするため. 欄も出さないので隠れたまま残さない). 異常の検知に変えたときは分割を変えない (選び直しを利用者に任せ, 欄の下の誤りで知らせる)
- **分析の正解の数**: 前処理のタスク (編集中のレシピ, 無ければ保存したレシピのもの) が異常の検知の場合, 分析を `task=anomaly` で求め (`GET /api/sources/{id}/profile?task=anomaly`), 概要と気付きのタブに ML-EDA の `profile` の `anomaly` から, 正解の列, 正解の付いた行, 異常の行, 異常の割合 (0 か 1 の正解の行のうち), 正解の欠けた行, 欠けた行も正常と見なした場合の異常の割合 (`presumed_ratio`. `split.unlabeled: normal` で書き出す割合) と, 収まらない値の行があればその数と例を出す (前処理のレシピを組む前に, 正解が少なすぎる表や異常が多すぎる表を見分けるため. 全ての行で数える). 目的の列を選ばないと, 正解の列が無いので全ての行を正常と見なすと出す. タスクが異常の検知の間は, 目的の列の有る無しによらず, 気付きも異常の検知の決まり (`class_imbalance` と `target_missing` の代わりに `label_invalid` と `few_anomalies`) になる. タスクか目的の列を変えると分析を求め直す. 求め直す間は前の分析を出したままにし, 前処理のタブの「学習できる形にする手順を作る」と「気付きから手順を足す」を止めて, 分析を求め直していることを理由として出す (前のタスクの気付きで手順を組まないため)
- **正解の欠けた行と手順の案**: タスクが異常の検知の間は, 気付きから足す手順と学習できる形にする手順に, 目的の列の欠けた行を落とす手順を入れない (正解の欠けた行を正常と見なして残すので, 落とすと正常の行が減るため. タスクを変えた直後の前の分析の `target_missing` にも効かせる)
- **正解の数と異常の割合**: 全ての手順の後の「学習用のデータ」に, ML-EDA の `prepare` の `anomaly` (書き出しの説明の `anomaly` と同じ形) から, 正解の付いた行 (正常と異常の正解の行), 異常の行, 正常と見なした行, 異常の割合と, 分割ごとの正常, 正常と見なした, 異常, 正解なし (`unlabeled` の分割) の行の数の表を出す. 異常の割合は, 正常の行 (正解が正常の行と, 正常と見なした行) と異常の行を合わせた数に対する異常の行の割合 (異常の行にだけ印を付けた表でも意味のある割合にするため. 正解なしの行は数えない). 正解の列の無い表は, 正解が無いことを添える. 書き出しの結果と, データセットの一覧の版 1 の異常の検知のデータセットにも, 説明の `anomaly` から同じ表を出す
- **学習のスクリプトでの使い方**: 書き出した後の例は, 学習用が正常の行だけであることと, 検証用とテスト用の正解 (異常は 1) で度合いを確かめることを添える. モデルを組むときの数と一覧の出す値は, 自己符号化器のモデルが入力を作り直す値の数 (学習に使う列の数と同じ) (ML-EDA の `model_inputs` の `outputs`) と添える (クラスの数と取り違えないように)
- **問題から始める**: 「問題から始める」で異常の検知の問題を選ぶと, 列の予測と同じく ML-Quest の `recipe_from` のレシピ (`task: anomaly`, 正解の列と行の id の列 (答えたときだけ), 度合いに使わない列を落とす手順, 標準化, 無作為の分割, 正解の列があれば `split.unlabeled: normal`) で始め, 入れた表を登録してレシピを保存する. 目的の列はレシピの正解の列 (無ければ目的の列を持たない). 登録する前に, データの種類が表か時系列であることと, 正解の列と行の id の列が表にあることを確かめ, 違えば理由を 422 で返して登録しない. 食い違いの確かめ, 書き戻しと「学習のプロジェクトへ書き出す」は列の予測と同じ流れ (ML-Quest の `apply_recipe` が異常の検知のレシピを確かめ, 書き戻す). ML-Quest が異常の検知の問題を受けない場合 (異常の検知の問いに答えていない, 異常の検知を知らない版など) は, ML-Quest の理由を「問題を渡せません」として出す (一覧の始められない理由も)

## 16. 介入の記録の表の分析

過去に行動した記録の表 (クーポンを配った記録. 顧客の特徴の列, 処置の列, 結果の列) を, 登録した表のまま分析し, 処置の群と対照の群の大きさ, 結果の差, 特徴の釣り合いと気付きを見てから, 顧客ごとの効果を見積もる学習のデータセットを版 1 の `task: uplift` で書き出す (ML-EDA の「介入の記録の要約」と「介入の記録の表」). 要約と分け方は ML-EDA の `describe_uplift`, `prepare` と `export_dataset` が行い, このアプリはレシピの欄と, ML-EDA が返す数を並べるだけを受け持つ (群の数え方と, 全ての分割に両方の群を置く決まりを, ML-EDA と ML-Quest の効果を見積もるの骨組みにそろえるため). 処置は無作為に配った記録を前提にする (偏りのある記録の傾向の見積もりは ML-EDA の約束の外).

- **どのデータで**: 種類が表か時系列のデータ (ML-EDA が他の種類の効果を見積もるを誤りにするため). 他の種類ではタスクの「効果を見積もる」を選べない (異常の検知と同じ)
- **結果の列**: 上の目的の列の欄で選ぶ (レシピの `target`). 目的の列が無ければ, 処置の列の説明に, 上で結果の列を目的の列に選ぶよう出す
- **処置の列**: 処置の群は 1 か真, 対照の群は 0 か偽の列 (レシピの `treatment`). 候補は目的の列と行の id の列を除いた列. 選んだ列は学習に使う列から除かれ, 全ての分割に 0 と 1 で残る (ML-EDA の決まり). 目的の列か行の id の列を処置の列にすると, 処置の列の指定を消す (ML-EDA が誤りにするため)
- **結果の種類**: 「値から決める」(書かない), 「起きたか」(`binary`. 買ったかの 0 と 1), 「量」(`amount`. 買った額) から選ぶ (レシピの `outcome`)
- **行の id の列**: 異常の検知と同じ (上の「15. 異常の検知の表の分析」. 候補は, 分析で欠けも同じ値も無い列から目的の列と処置の列を除いたもの)
- **分割**: 層化だけ (処置で層を作り, 結果が起きたかなら処置と結果の組で層を作る. 全ての分割に処置の群と対照の群を置く. ML-EDA の決まり). 他の分け方は選べず, 残っていれば欄の下に誤りを出す. 検証用とテスト用の割合は上の欄で選ぶ
- **正解の欠けた行**: 結果の欠けた行を, 落とす (既定) か `unlabeled` の分割に残すかを選ぶ. 「正常と見なす」は選べない
- **タスクを変えたら**: 効果を見積もるから他のタスクに変えると, 処置の列と結果の種類を消し, 異常の検知でなければ行の id の列も消す (ML-EDA が他のタスクで誤りにするため. 欄も出さないので隠れたまま残さない). 異常の検知から効果を見積もるに変えると「正常と見なす」を消す. 効果を見積もるに変えたときは分割を変えない (選び直しを利用者に任せ, 欄の下の誤りで知らせる)
- **介入の記録の要約**: タスクが効果を見積もるで, 結果の列と処置の列を選ぶと, 前処理のタブの欄の下に ML-EDA の `describe_uplift` の結果を出す (`POST /api/sources/{id}/uplift`. 前処理の手順をかける前の表で数える. 手順を組む前に群の大きさと前提の崩れを見るため). 処置と結果の両方が分かる行, 処置の群と対照の群の行の数と結果の平均, 処置の割合, 結果の平均の差 (全体の効果), 欠けた行の数 (処置と結果), 釣り合いの表 (列, 型, 標準化した平均の差, カテゴリの列は最も差の大きい値. 差の絶対値が 0.25 以上の行に「釣り合いが崩れ」の印. 表の上に, 0 に近いほど群がそろうことと, 0.1 未満ならよくそろい 0.25 以上なら崩れているという読み方を添える), 気付き (片方の群が少なすぎる (`small_group`), 無作為に配った記録に見えない (`treatment_imbalance`), 処置の後に決まる列 (`post_treatment`), 処置か結果の欠けた行). 処置の後に決まる列の気付きには, その列を落とす手順を足す押しボタンを置く (効果の見積もりに使うと効果を取り違えるため). 結果の種類と行の id の列は欄の値を渡し, 釣り合いの列は渡さない (ML-EDA の既定で, 処置, 結果, 行の id の列を除く数, 真偽, カテゴリの列). 行の id の列を選んでいなければ, ID らしい列も釣り合いの表に入るので, 行の id の列を選ぶとその列が表から外れることを添える. 処置の群と対照の群は, 処置の列の説明, 要約と群の数の表で, 処置の列が 1 の行と 0 の行だと添える (初めての利用者が数を読めるように). 欄を変えると要約を求め直す
- **群の数と結果の差**: 全ての手順の後の「学習用のデータ」に, ML-EDA の `prepare` の `uplift` (書き出しの説明の `uplift` と同じ形) から, 処置の列, 結果の種類と, 分割ごとの処置の群と対照の群の行の数, 群ごとの結果の平均と差の表を出す (`unlabeled` の分割は数だけ). 書き出しの結果と, データセットの一覧の版 1 の効果を見積もるのデータセットにも, 説明の `uplift` から同じ表を出す
- **学習のスクリプトでの使い方**: 書き出した後の例は, 処置の列が学習に使う列に入らず `dataset.treatment(split)` で読むことと, 分割ごとの群の数と結果の差が `dataset.info["uplift"]["splits"]` にあることを添える. モデルを組むときの数と一覧の出す値は, 処置したときの予測と, しないときの予測で, それぞれ 1 件に 1 つの値を出すと添える (画面では「出力の頭」の言葉を使わない) (ML-EDA の `model_inputs` の `outputs`)
- **問題から始める**: 「問題から始める」で効果の見積もりの問題を選ぶと, 列の予測と同じく ML-Quest の `recipe_from` のレシピ (`task: uplift`, 結果の列, 処置の列, 結果の種類, 行の id の列 (答えたときだけ), 見積もりに使わない列を落とす手順, 標準化, 処置で層を作る分割, 結果の欠けた行は落とす) で始め, 入れた表を登録してレシピを保存する. 目的の列はレシピの結果の列. ML-Quest の受け渡し (`handoff`) は最上位の `uplift` (処置の列, 結果の列, 結果の種類, 行の id の列, 見積もりに使う列, 上位の割合) と, データの分析の値 (`task: uplift`, `split: stratified`, `treatment`, `outcome_kind`) を持ち, レシピの雛形はその値で作られる. 登録する前に, データの種類が表か時系列であることと, 結果の列, 処置の列, 行の id の列が表にあることを確かめ, 違えば理由を 422 で返して登録しない. 食い違いの確かめ, 書き戻しと「学習のプロジェクトへ書き出す」は列の予測と同じ流れ (ML-Quest の `apply_recipe` が効果の見積もりのレシピを確かめ, 書き戻す). ML-Quest が効果の見積もりの問題を受けない場合 (効果の見積もりの問いに答えていない, 効果の見積もりを知らない版など) は, ML-Quest の理由を「問題を渡せません」として出す (一覧の始められない理由も)

## 17. 値段を変えた記録の表の分析

過去の売れ行きの記録の表 (商品の id の列, 商品の特徴の列, 値段の列, 売れた数の列, 原価の列 (任意)) を, 登録した表のまま分析し, 値段の幅と数, 値段と売れた数の関わり, 商品ごとの試した値段, 値段と他の列の関わりと気付きを見てから, 値段を変える判断の学習のデータセットを版 1 の `task: price` で書き出す (ML-EDA の「値段を変えた記録の要約」と「値段を変えた記録の表」). 要約と分け方は ML-EDA の `describe_price`, `prepare` と `export_dataset` が行い, このアプリはレシピの欄と, ML-EDA が返す数を並べるだけを受け持つ (値段の段の数え方と, 値段の列にかけられる手順の決まりを, ML-EDA と ML-Quest の値段を変える判断の骨組みにそろえるため). 値段は試しに変えた記録 (無作為に近い) を前提にする (偏りのある値段の記録は ML-EDA の約束の外).

- **どのデータで**: 種類が表か時系列のデータ (ML-EDA が他の種類の値段を変える判断を誤りにするため). 他の種類ではタスクの「値段を変える判断」を選べない (効果を見積もると同じ)
- **売れた数の列**: 上の目的の列の欄で選ぶ (レシピの `target`). 目的の列が無ければ, 値段の列の説明に, 上で売れた数の列を目的の列に選ぶよう出す
- **値段の列**: 売ったときの値段の列 (レシピの `price`. 0 より大きい数). 候補は数の列 (真偽値を除く. 分析の型は値の少ない整数をカテゴリにするので, 読み込んだ型で見る) から目的の列と行の id の列を除いたもの. 他の役割の列 (原価の列, 商品の id の列) は選ぶと, その欄の指定を消す. 値段の列は学習に使う列の最後に残る (ML-EDA の決まり)
- **原価の列** (任意): 商品 1 つを仕入れるか作るのにかかる値段の列 (レシピの `cost`. 0 以上の数). 候補は値段の列と同じ決まり. 学習に使う列から除かれ, 書き出す全ての分割に元の値で残る. 選ばなければ利益は原価を 0 として売上で数える (ML-EDA の決まり)
- **商品の id の列** (任意): 値段を選ぶ単位の商品を指す列 (レシピの `product`. 同じ商品の行は何行あってもよい). 候補は目的の列と行の id の列を除いた列. 他の役割の列 (値段の列, 原価の列) は選ぶと, その欄の指定を消す. 学習に使う列から除かれ, 書き出す全ての分割にそのまま残る
- **行の id の列**: 異常の検知と同じ (上の「15. 異常の検知の表の分析」. 候補は, 分析で欠けも同じ値も無い列から目的の列, 値段の列, 原価の列, 商品の id の列を除いたもの)
- **列の重なり**: 売れた数, 値段, 原価, 商品の id, 行の id の列は互いに違う列 (ML-EDA が誤りにするため). 1 つの欄で他の欄と同じ列を選ぶと, 他の欄の指定を消す. 目的の列を値段, 原価か商品の id の列と同じにすると, その欄の指定を消す
- **値段の手順**: 値段の列の値を変えられる手順は値段の手順 (`clip`, `log`, `standardize`, `minmax`) だけ. 行を絞る手順 (`filter_rows`, `drop_missing`, `drop_duplicates`) は値段の列を見てよい. 列を落とすなど他の手順の列の候補に値段の列を出さない. 原価の列と商品の id の列は, 列を落とす手順と, 列を選ぶ行を絞る手順 (`drop_missing`, `drop_duplicates`) の候補にだけ出す (ML-EDA が他の手順で名前を書くと誤りにするため). 読み込んだレシピなどで他の手順の列に値段の列があれば, 手順の欄の下に誤りを出す. 値段の手順の `columns: auto` は値段の列も選ぶ (ML-EDA の決まり)
- **分割**: 層化だけ (値段の段で層を作り, 値段の高い行と低い行を全ての分割に置く. ML-EDA の決まり). 他の分け方は選べず, 残っていれば欄の下に誤りを出す. 検証用とテスト用の割合は上の欄で選ぶ
- **正解の欠けた行**: 売れた数の欠けた行を, 落とす (既定) か `unlabeled` の分割に残すかを選ぶ. 「正常と見なす」は選べない
- **タスクを変えたら**: 値段を変える判断から他のタスクに変えると, 値段の列と原価の列を消し, 時間をまたぐ量の判断でなければ商品の id の列も, 異常の検知, 効果を見積もる, 時間をまたぐ量の判断でなければ行の id の列も消す (ML-EDA が他のタスクで誤りにするため. 欄も出さないので隠れたまま残さない). 異常の検知から変えると「正常と見なす」を消す. 値段を変える判断に変えたときは分割を変えない (選び直しを利用者に任せ, 欄の下の誤りで知らせる)
- **値段を変えた記録の要約**: タスクが値段を変える判断で, 売れた数の列と値段の列を選ぶと, 前処理のタブの欄の下に ML-EDA の `describe_price` の結果を出す (`POST /api/sources/{id}/price`. 前処理の手順をかける前の表で数える. 手順を組む前に値段の幅と前提の崩れを見るため). 使う行の数, 欠けた行と値の誤りの行の数, 値段の最小, 最大, 中央値, 種類の数と幅, 売れた数の最小, 最大, 平均と 0 の行の割合, 値段と売れた数の順位の相関と弾力性の目安, 値段の段ごとの行の数, 値段の範囲と売れた数の平均の表, 商品の id の列を選んだ場合の商品の数, 試した値段が 1 つの商品の数と商品ごとの試した値段の表 (試した値段の少ない順), 原価の列を選んだ場合の原価の平均, 値段に対する利幅の平均と値段が原価より低い行の数, 値段と他の列の関わりの表 (列, 型, 強さ. 強さが 0.3 以上の行に「値段と強く関わる」の印. 表の上に, 0 に近いほど値段を無作為に近く変えた記録に見えるという読み方を添える), 気付き (値段の欠けと誤り, 値段の種類が少なすぎる (`few_prices`), 試した値段が 1 つの商品 (`single_price_products`), 値段の幅が狭すぎる (`narrow_price_range`), 値段と強く関わる列 (`price_confounded`), 値段が原価より低い行 (`price_below_cost`) など). 弾力性は, 値段を 1 % 上げたときに売れた数が何 % 変わるかの目安で, 負なら値段を上げると売れた数が減ると添える (初めての利用者が数を読めるように). 幅は (最大 − 最小) / 中央値で, 商品の id の列を選ぶと商品ごとの幅の中央値になると添える. 原価, 商品の id, 行の id の列は欄の値を渡し, 関わりの列は渡さない (ML-EDA の既定で, 値段, 売れた数, 原価, 商品の id, 行の id の列を除く数, 真偽, カテゴリの列). 欄を変えると要約を求め直す
- **値段の範囲と売れた数**: 全ての手順の後の「学習用のデータ」に, ML-EDA の `prepare` の `price` (書き出しの説明の `price` と同じ形) から, 値段の列, 元の値段の列, 原価の列, 商品の id の列, 行の id の列, 売れた数の欠けた行の扱い, 値段の列にかけた値段の手順と, 分割ごとの行の数, 商品の数, 元の値段の最小と最大と種類の数, 売れた数の平均, 原価の平均の表を出す (`unlabeled` の分割は売れた数の平均を出さない). 書き出しの結果と, データセットの一覧の版 1 の値段を変える判断のデータセットにも, 説明の `price` から同じ表を出す
- **学習のスクリプトでの使い方**: 書き出した後の例は, 値段の列が学習に使う列の最後にあることと, 候補の値段での入力を `dataset.price_inputs(split, prices)` で, 元の値段を `dataset.price(split)` で, 原価を `dataset.cost(split)` で読むことと, 分割ごとの値段の範囲が `dataset.info["price"]["splits"]` にあることを添える. モデルを組むときの数と一覧の出す値は, 売れた数の予測で 1 件に 1 つの値を出すと添える (ML-EDA の `model_inputs` の `outputs`)
- **問題から始める**: 「問題から始める」で値段を変える判断の問題を選ぶと, 効果の見積もりと同じく ML-Quest の `recipe_from` のレシピ (`task: price`, 売れた数の列, 値段の列, 原価の列, 商品の id の列と行の id の列 (答えたときだけ), 予測に使わない列を落とす手順, 標準化, 値段の段で層を作る分割, 売れた数の欠けた行は落とす) で始め, 入れた表を登録してレシピを保存する. 目的の列はレシピの売れた数の列. ML-Quest の受け渡し (`handoff`) は最上位の `price` (値段, 売れた数, 原価, 商品の id, 行の id の列と予測に使う列) と, データの分析の値 (`task: price`, `split: stratified`, `known` (予測に使う列と, 最後に値段の列)) を持ち, レシピの雛形はその値で作られる. 登録する前に, データの種類が表か時系列であることと, 売れた数の列, 値段の列, 原価の列, 商品の id の列, 行の id の列が表にあることを確かめ, 違えば理由を 422 で返して登録しない. 食い違いの確かめ, 書き戻しと「学習のプロジェクトへ書き出す」は列の予測と同じ流れ (ML-Quest の `apply_recipe` が値段を変える判断のレシピを確かめ, 書き戻す). ML-Quest が値段を変える判断を知らない版 (値段の列の問い `ml.parts.0.price.price` を持たない) では, 効果の見積もりと取り違えないように, 「問題を渡せません」と, ML-Quest を値段を変える判断を受ける版に上げるよう出して止まる (一覧の始められない理由も). 値段を変える判断の問いに答えていない場合などは, ML-Quest の理由を「問題を渡せません」として出す

## 18. 需要の記録の表の分析

商品ごとの日ごとの売れた数の記録の表 (商品の id の列, 日付の列, 日ごとの売れた数の列, 商品の特徴の列, 在庫の数の列 (任意)) を, 登録した表のまま分析し, 日付の範囲, 売れた数, 曜日ごとの売れた数, 商品ごとの記録の日数と抜けの日, 在庫が 0 の日と気付きを見てから, 時間をまたぐ量の判断の学習のデータセットを版 1 の `task: demand` で書き出す (ML-EDA の「需要の記録の要約」と「需要の記録の表」). 読み込む表は 1 行が (商品, 日) で, 書き出す 1 行は (商品, 発注を決める日), 正解は先の期間の売れた数の合計. 要約と発注を決める日の行の作り方と分け方は ML-EDA の `describe_demand`, `prepare` と `export_dataset` が行い, このアプリはレシピの欄と, ML-EDA が返す数を並べるだけを受け持つ (期間の合計の作り方と, 分割の境目をまたぐ行の落とし方を, ML-EDA と学習の段階にそろえるため). 学ぶ分位点の水準と発注の数の決め方は学習と推論の段階の約束で, この画面では決めない. タスクの名前は ML-EDA の需要の予測 (`task: demand`) で, 画面の言葉は問題の課題の名前にそろえて「時間をまたぐ量の判断」と呼ぶ.

- **どのデータで**: 種類が表か時系列のデータ (ML-EDA が他の種類の需要の予測を誤りにするため. 日付の列を見つけた表は時系列として読まれる). 他の種類ではタスクの「時間をまたぐ量の判断」を選べない (値段を変える判断と同じ)
- **日ごとの売れた数の列**: 上の目的の列の欄で選ぶ (レシピの `target`). 目的の列が無ければ, 商品の id の列の説明に, 上で売れた数の列を目的の列に選ぶよう出す. 書き出しの正解は ML-EDA が作る先の期間の合計の列 (`demand`) で, 日ごとの売れた数の列は学習に使う列に入らない
- **商品の id の列**: 発注の数を決める単位の商品を指す列 (レシピの `product`. 必ず選ぶ). 候補は目的の列と行の id の列を除いた列. 学習に使う列から除かれ, 書き出す全ての分割にそのまま残る
- **日付の列**: 1 行が 1 日の記録の日付の列 (レシピの `date`. 必ず選ぶ). 候補は数と真偽値でない列 (読み込んだ型で見る. ML-EDA が数か真偽値の日付の列を誤りにするため) から目的の列と行の id の列を除いたもの. 学習に使う列から除かれ, 書き出す全ての分割に発注を決める日で残る. 曜日や月は `datetime_parts` で列にする
- **在庫の数の列** (任意): その日の始めの在庫の数の列 (レシピの `stock`. 0 以上の数). 候補は値段の列と同じく数の列 (真偽値を除く) から目的の列と行の id の列を除いたもの. 学習に使う列から除かれ, 書き出す全ての分割に元の値で残る. 推論の段階は予測した需要から在庫の数を引いて発注する
- **期間**: 先の期間の日数 (レシピの `horizon`) と発注を決める日の間隔 (レシピの `interval`) を数で入れる. 空か 1 未満か整数でない値は項目を消し, ML-EDA の既定 (先の期間は 7 日, 間隔は先の期間と同じ) を使う (既定を書かないレシピと見分けないため). 間隔を先の期間より短くすると, 分割の境目をまたぐ行を ML-EDA が落とすことを欄の下に添える
- **行の id の列**: 異常の検知と同じ (上の「15. 異常の検知の表の分析」. 候補は, 分析で欠けも同じ値も無い列から目的の列, 商品の id の列, 日付の列, 在庫の数の列を除いたもの)
- **列の重なり**: 売れた数, 商品の id, 日付, 在庫の数, 行の id の列は互いに違う列 (ML-EDA が誤りにするため). 1 つの欄で他の欄と同じ列を選ぶと, 他の欄の指定を消す. 目的の列を商品の id, 日付か在庫の数の列と同じにすると, その欄の指定を消す
- **手順**: 商品の id と在庫の数の列は, 列を落とす手順と, 列を選ぶ行を絞る手順 (`drop_missing`, `drop_duplicates`) の候補にだけ出す (ML-EDA が他の手順で名前を書くと誤りにするため). 過去の売れた数は `lag` で列にし, ML-EDA の決まり (値を学ぶ最初の手順より前に置く, `by` に商品の id の列, `time` に日付の列, `lags` は 1 以上の整数) に合わない `lag` と, 他の手順に名前で書いた商品の id か在庫の数の列は, 手順の欄の下に誤りを出す (前処理を試す前に直す所が分かるように). 値を学ぶ手順かは `GET /api/info` の手順の `fits` で見分ける. 商品の id と日付の列を選び, `lag` がまだ無ければ, 「過去の売れた数と曜日の手順を足す」で, 1 日前と 7 日前の売れた数, 前の 7 日と 28 日の平均 (`lag` の `columns: [<売れた数の列>]`, `by`, `time`, `freq: 1D`) と曜日と月 (`datetime_parts`) を手順の先頭に足せる (ML-EDA の約束の例と同じ形. 初めての利用者が決まりに合う手順を組めるように)
- **分割**: 時刻の順だけ (発注を決める日の順に分け, 先の期間が後の分割に入らないようにする. ML-EDA の決まり). 他の分け方は選べず, 残っていれば欄の下に誤りを出す. 検証用とテスト用の割合は上の欄で選ぶ
- **正解の欠けた行**: 先の期間の合計の分からない発注を決める日の行 (記録の終わりの近くの日と, 先の期間に抜けの日のある日) を, 落とす (既定) か `unlabeled` の分割に残すかを選ぶ. 「正常と見なす」は選べない
- **タスクを変えたら**: 時間をまたぐ量の判断から他のタスクに変えると, 日付の列, 在庫の数の列と期間を消し, 値段を変える判断でなければ商品の id の列も, 異常の検知, 効果を見積もる, 値段を変える判断でなければ行の id の列も消す (ML-EDA が他のタスクで誤りにするため. 欄も出さないので隠れたまま残さない). 時間をまたぐ量の判断に変えたときは分割を変えない (選び直しを利用者に任せ, 欄の下の誤りで知らせる)
- **需要の記録の要約**: タスクが時間をまたぐ量の判断で, 売れた数の列, 商品の id の列と日付の列を選ぶと, 前処理のタブの欄の下に ML-EDA の `describe_demand` の結果を出す (`POST /api/sources/{id}/demand`. 前処理の手順をかける前の日ごとの表で数える. 手順を組む前に記録の抜けと短さを見るため). 使う行の数, 日付の範囲と日数, 商品の数, 売れた数の最小, 最大, 平均と 0 の日の割合, 記録の短い商品の数, 抜けの日のある商品の数と抜けの日の合計, 在庫の数の列を選んだ場合の在庫が 0 の日の行と割合と商品の数, 欠けた行, 値の誤りの行と同じ商品の同じ日の行の数, 気付き (`date_gaps`, `short_history`, `stockout_days` など), 曜日ごとの行の数と売れた数の平均の表, 商品ごとの記録の日数, 最初と最後の日, 抜けの日, 在庫が 0 の日, 売れた数の平均の表 (記録の日数の少ない順に 20 商品まで. 記録の短い商品の日数と, 抜けの日と在庫が 0 の日のある数を注意の色で) を出す. 記録の短い商品は記録の日数が先の期間の 4 倍未満の商品で, 前の期間と先の期間で先の期間の 2 倍の日を使うので書き出す行がわずかか作れないと添え, 抜けの日を含む期間は合計を作らず, 売れなかった日なら売れた数 0 の行を足すよう添え, 在庫が 0 の日の売れた数は需要より少なく記録されると添える (初めての利用者が数を読めるように). 先の期間の日数は欄の値を渡す (空なら既定の 7). 欄を変えると要約を求め直す
- **発注を決める日と期間の合計**: 全ての手順の後の「学習用のデータ」に, ML-EDA の `prepare` の `demand` (書き出しの説明の `demand` と同じ形) から, 1 行の意味 (商品, 発注を決める日), 正解の列と比べる相手の列, 先の期間の日数と間隔, 商品の id, 日付, 日ごとの売れた数, 在庫の数, 行の id の列, 先の期間の合計の分からない行の扱い, 落とした行の数 (前の期間が揃わない行と分割の境目をまたぐ行) と, 分割ごとの行と商品の数, 発注を決める日の最初と最後, 先の期間と前の期間の合計の平均, 先の期間に在庫が 0 の日を含む行の数の表を出す (`unlabeled` の分割は先の期間の合計の平均を出さない). 書き出しの結果と, データセットの一覧の版 1 の時間をまたぐ量の判断のデータセットにも, 説明の `demand` から同じ表を出す
- **学習のスクリプトでの使い方**: 書き出した後の例は, 正解が先の期間の売れた数の合計 (`demand`) であることと, 前の期間の合計を `dataset.previous(split)` で, 在庫の数を `dataset.stock(split)` で読むことと, 先の期間の日数と分割ごとの発注を決める日の範囲が `dataset.info["demand"]` にあることを添える. モデルを組むときの数と一覧の出す値は, ML-EDA の `model_inputs` の `outputs` (分位点の水準 1 つあたりの値の数. 1) で, 最後の層の出す数はこれに学ぶ水準の数 (問題の設定の段階で決める) をかけた数と添える
- **問題から始める**: 「問題から始める」で時間をまたぐ量の判断の問題を選ぶと, 値段を変える判断と同じく ML-Quest の `recipe_from` のレシピ (`task: demand`, 日ごとの売れた数の列, 商品の id の列, 日付の列, 在庫の数の列 (答えたときだけ), 先の期間の日数, 行の id の列 (答えたときだけ), 予測に使わない列を落とす手順, 商品ごとの過去の売れた数 (`lag`), 曜日, 標準化, 発注を決める日の順の分割) で始め, 入れた表を登録してレシピを保存する. 目的の列はレシピの日ごとの売れた数の列. 登録する前に, データの種類が表か時系列であることと, 日ごとの売れた数の列, 商品の id の列, 日付の列, 在庫の数の列, 行の id の列が表にあることを確かめ, 違えば理由を 422 で返して登録しない. 食い違いの確かめ, 書き戻しと「学習のプロジェクトへ書き出す」は値段を変える判断と同じ流れ (ML-Quest の `apply_recipe` が時間をまたぐ量の判断のレシピを確かめ, 列と先の期間の日数を答えのままにして書き戻す). ML-Quest が時間をまたぐ量の判断を知らない版 (骨組みの型 `SKELETON_TYPES` に `demand` を持たない) では, 答え (予測するで, 正解の種類が先の期間の需要, 作り方が既製のモデルをそのままでない) で見分け, 「問題を渡せません」と, ML-Quest を時間をまたぐ量の判断を受ける版に上げるよう出して止まる (一覧の始められない理由も). 時間をまたぐ量の判断の問いに答えていない場合などは, ML-Quest の理由を「問題を渡せません」として出す

## 19. 課題の型への広げ方

機械学習の課題は「予測する」のほかに「作る」「並べる」「まとめる」「効果を見積もる」に分けられ, 正解の出どころ, 1 件の単位, 作り方でデータの形と確かめ方が変わる (詳しくは ML-EDA の設計の同じ節). 分析と書き出しの仕組みは ML-EDA に足し, この画面はそれを使う.
